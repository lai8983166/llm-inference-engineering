## Why

第 02 章已经把多请求执行收束为“下一次该选择哪些可运行工作”，但这个问题还缺少最关键的容量输入：每个请求都在持续积累后续 token 仍要读取的 K/V 状态。若直接进入分页 KV，学习者容易把 block table 当成框架技巧，而没有先理解 KV 为什么必须保存、占多少、为何增长，以及连续内存方案究竟被什么约束击穿。

## What Changes

- 新增第 03 章“KV 为什么成为系统状态”，从一次 Attention 计算中哪些历史量会被下一 token 复用开始，连续推导 KV cache 的必要性、生命周期与请求所有权。
- 使用一个固定模型配置和第 02 章延续的长短请求，逐步建立单 token、单层、单请求和多请求 KV 字节账本，并把 dtype、层数、KV head 数、head dimension 与序列长度纳入可复核公式。
- 认真分析“按最大长度一次预留”和“按需连续扩容”两个合理方案，分别用未知输出长度、扩容复制、外部碎片、并发到达与独立回收暴露失败，而不把连续分配写成稻草人。
- 将逻辑 token 位置、物理地址、已用容量、保留容量、在途读取和释放许可分开，使学习者能判断 OOM 来自有效 KV、过度预留、暂时复制峰值还是无法利用的碎片。
- 只在张量复用、容量增长和地址搬迁难以由文字观察时加入少量可暂停、单步图示；是否保留分配推演仍由完整正文后的认识增量评审决定。
- 章节止于“逻辑上连续增长的序列是否必须占据连续物理区间”这一设计问题，为第 04 章从碎片推导分页 KV 建立需求，不提前给出 block、page、block table 或生产 allocator 答案。
- 不在本章实现 paged attention、生产 KV allocator、prefix cache、抢占、offload、量化 KV 或真实 GPU 性能比较。

无。
