## Context

第 01 章已经建立单请求执行器、请求级状态与终止清理合同；第 00 章建立了从原始事件到有边界结论的证据规则。第 02 章要复用这两层认识，把唯一变化限制为“多个请求同时存在”，见 `proposal.md` 与 `specs/naive-concurrency-chapter/spec.md`。

当前站点以 MDX 承载连续正文，以 React/TypeScript 组件呈现必须观察的状态变化。前两章已证明动态图可以嵌在因果链之后，但也暴露了两个持续约束：不能把长话题拆成卡片堆，视觉控制也不能遮住标题、原始数据或静态退化内容。

本章不假设真实 GPU 能够并行执行多少 kernel，也不把某种事件轨迹写成 vLLM 或 SGLang 的当前实现。可移植内容使用确定性的抽象设备步；有关 stream、kernel overlap、batch kernel 效率或实际吞吐的判断只说明需观察什么，不预先给出硬件结论。

## Goals / Non-Goals

**Goals:**

- 用同一组长短请求把“正确的单请求循环”连续推进到串行、多循环和静态 batch，保留每一步为什么合理以及为何仍然失败。
- 建立到达、等待、可运行、被选中、设备完成和终止的最小事件模型，使排队与执行成本不会混为一谈。
- 通过少量、问题单一的动态图观察多请求交错和 batch 槽位变化，同时保持正文在隐藏图示后仍可独立成立。
- 把本章结论收束为下一次执行选择所需的信息和不变量，而不是提前展示 continuous batching 的实现。
- 通过新轨迹检查学习者能否迁移诊断、保护请求语义并限定模拟证据。

**Non-Goals:**

- 不实现真实模型执行、网络服务器、GPU stream、paged KV allocator 或生产 scheduler。
- 不系统定义 TTFT、ITL、吞吐、goodput、开放环和闭环；本章只保留理解等待来源所需的事件。
- 不比较真实框架性能，不把确定性教学步换算为毫秒或硬件利用率。
- 不在本章决定准入、抢占、优先级或公平性算法，也不把未来调度问题收束成唯一策略。

## Decisions

### 1. 用一组固定请求连续改变执行组织

正文使用三到四个请求组成的确定性工作负载，其中至少包含先到的长请求、晚到的短请求、不同 prompt 长度和不同输出终止步数。每个请求沿用第 01 章的独立身份、生成状态、输出与清理语义；后续比较只能改变工作如何排队、提交或组合。

认知推进分为五次转折：

1. 单请求循环复制到服务后，最安全的办法是排队逐个完成。
2. 串行保持语义，却让晚到短请求的等待由前一个长请求决定。
3. 每请求一个线程或协程让主机控制流交错，但没有自动定义设备执行或批量工作。
4. 静态 batch 用一次执行容纳多个请求，却要求成员在形状与生命周期上暂时对齐。
5. 长度差异、提前结束和晚到请求让固定成员失效，从而形成“每个执行边界重新选择哪些工作”的问题。

标题只对应这些认知转折；concurrency、parallelism、batch、padding、head-of-line blocking 等名称在对应矛盾出现后解释。替代方案是按概念建立独立小节或并列方案卡片，虽然便于检索，却会把一条演进重新切成术语目录，因此不采用。

### 2. 抽象设备步只表达因果关系，不伪装耗时模型

确定性数据层采用离散事件和逻辑工作单位：

- `RequestFixture`：请求标识、到达步、prompt token 数、预定生成 token 数和终止原因。
- `RequestSnapshot`：等待或运行阶段、剩余逻辑工作、是否可运行、是否在途、资源是否已释放。
- `ExecutionGroup`：一次抽象设备执行包含的请求、phase、各成员有效 token 数、padding 或非活跃槽位。
- `ConcurrencyEvent`：逻辑时刻、请求、事件类型、可选执行组和产生该事件的策略。
- `StrategyTrace`：固定工作负载在串行、独立循环或静态 batch 假设下生成的完整事件序列。

逻辑步只允许证明事件先后、等待来源、有效工作和占位浪费。界面与正文不得把它标成毫秒、GPU utilization 或真实吞吐；任何真实设备方向都回到第 00 章的测量合同。

替代方案是给每种操作赋任意耗时以绘制更像 profiler 的图，但这会让学习者把模型假设误读为硬件事实，因此只保留相对事件边界。

### 3. 串行与独立循环共享一张因果轨迹，静态 batch 使用另一张占用图

第一张图把请求泳道、主机提交与抽象设备执行放在同一逻辑时间轴上。它允许在“串行”和“独立循环”之间切换，但始终显示相同到达事件；切换后只改变可运行请求何时提交以及设备事件如何排列。独立循环模式明确呈现“主机已活跃”与“设备实际开始”是两种状态，且不模拟未经证明的 kernel overlap。

第二张图展示静态 batch 内 prompt 对齐和逐步 decode：横向是执行步，纵向是 batch 成员，每格区分有效 token、为形状对齐的 padding、成员已结束后的空槽以及新请求在批外等待。这样可以同时看见形状浪费和策略等待，却不把两者合成一个百分比仪表。

两图均从正文建立问题后出现，支持暂停、单步、重置和键盘操作。reduced-motion 下状态离散切换；窄屏优先保持标签与当前事件可读，必要时让内部轨迹区域滚动而不裁切章节文字。

替代方案是建立一个可自由切换全部策略、参数和指标的大型调度模拟器；它会在学习者形成事件模型前暴露过多控制，并提前暗示“调参找到最佳策略”，因此不采用。

### 4. 静态 batch 的两个失败必须分开推导

prefill 中的 prompt 长度差异用于解释为什么密集形状通常要对齐，以及 padding 代表执行了不属于有效 token 的位置。decode 中的输出长度差异则用于解释为什么固定成员提前结束后出现空槽、占位或重新组织批次的选择。晚到请求继续在封闭批次之外等待，用来暴露批次边界本身造成的策略延迟。

正文不会声称所有实现都必须以同一种 padding 方式运行，也不会把“空槽”直接等同某个真实 kernel 的浪费比例。工程讨论要写清楚每个候选处理方式改变的元数据、形状或同步合同，并把实际代价留给实现和测量。

### 5. 先完成无实践正文，再以主动重建增量决定是否保留推演

初始实现先交付完整正文、手算轨迹和两张解释性图。编辑评审暂时隐藏可操作实践，确认学习者已经能从请求事件推导三种朴素方案的失败。

之后只考虑一个短轨迹审查：给出未标注原因的新事件序列，让学习者先预测最早出现的等待或浪费，再把事件归类为“不可运行”“可运行未选择”“有效设备工作”“padding/空槽”，最后查看派生解释。只有它要求学习者主动重建状态、且与两张图不重复时才保留；否则删除实践，以迁移评估承担验收。

实践不会让学习者直接拼装 continuous batching，也不会产生完成进度。它使用同一纯函数数据边界并持续标注为模拟证据。

### 6. 章末验收换用新工作负载并要求先找首个因果缺口

迁移评估给出不同到达顺序和长度组合，其中同时包含晚到短请求、提前结束成员以及两个主机循环近邻提交。学习者依次完成：重建关键事件、指出第一个等待或浪费来源、说明为何主机活跃不能证明设备并行、列出必须保持的请求级不变量、提出下一次选择所需的最小状态。

结构化首问可以提供即时反馈；因果说明与调度输入采用自由文本加展开式检查标准，不做伪精确自动评分。验收关注迁移推理，不询问“continuous batching 是什么”。

### 7. 第 02 章加入稳定顺序但不制造尚不存在的第 03 章链接

首页与 README 更新为 00→01→02，第 01 章增加“下一章”入口，第 02 章提供返回第 01 章的入口。正文结尾可以说明下一步将进入 KV 状态与容量问题，但在第 03 章页面尚未实现前不生成失效链接；未来第 03 章交付时再补正向导航。

## Risks / Trade-offs

- **内容滑向调度算法预告，削弱后续章节推导** → 第 02 章只形成可运行集合、执行选择和请求不变量，不命名或实现动态 batch 策略。
- **抽象设备步被当作性能模型** → 使用“逻辑步”和事件计数，不显示毫秒与利用率；所有结论旁标注模拟边界并回指真实测量要求。
- **三种方案并列导致 PPT 式碎片** → 保持固定请求和未解问题，每个方案由上一方案的具体失败自然产生，移除独立优缺点卡片与重复总结。
- **图示控制过多使读者先玩参数** → 固定案例，只允许切换必要方案、暂停和单步；参数探索留给未来真正需要的调度实验。
- **静态 batch 解释把实现细节写成普遍规律** → 分开描述语义约束、教学模型假设和需实测的硬件行为，并在来源记录中分类。
- **第 02 章与第 05 章 continuous batching 重复** → 本章止于问题合同；第 05 章才让请求动态加入/退出并比较调度策略对服务指标的影响。

## Migration Plan

1. 建立第 02 章来源/编辑记录、确定性请求与事件数据层、MDX 载体和路由，提交独立基础批次。
2. 完成隐藏图示和实践也能成立的连续正文、手算轨迹与章节结构检查，进行 prose-only 评审后独立提交。
3. 逐张加入因果轨迹与 batch 占用图，验证事件一致性、暂停/单步、键盘、reduced-motion 和窄屏表现后独立提交。
4. 评估短轨迹推演的认识增量；保留或明确删除，再加入新的迁移验收并独立提交。
5. 更新 00→01→02 导航、README、全量测试和编辑记录，完成最终提交并交由用户验收。

改动只新增章节、确定性教学模型和导航，无持久数据迁移。若新章节导致回归，可撤回第 02 章入口与路由，不影响已经验收的第 00、01 章。
