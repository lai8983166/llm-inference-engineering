## Context

第 01 章已经把一次生成请求拆成模型执行、采样、输出可见与资源结束等事件，但学习者进入这些机制以前仍缺少一个更基础的判断框架：一个“正确”或“更快”的结论究竟需要什么证据。README 已把第 00 章列为共同主线入口，本次改动要把它做成可独立阅读的序章，而不是提前讲一遍第 08 章的压测体系。

现有站点使用 React、TypeScript、Vite 与 MDX，章节正文、教学图示和交互实践分层组织。第 01 章已经验证了 prose-first 的连续叙事与可暂停动态图可以共存，因此第 00 章延续其教学合同和技术底座，但不复刻页面构图、组件数量或视觉隐喻。

本章的受众可能只知道“调用模型得到结果”，不能预设其已理解 prefill、decode、CUDA event 或服务调度。所有设备执行概念先以“主机提交—设备完成”的黑盒事件解释；具体框架 API 只作为后续映射或真实设备分支，不承担概念定义。

## Goals / Non-Goals

**Goals:**

- 以“实现 B 快了 30%”这一项主张维持整章的问题连续性，每一步修复一个证据缺口并自然产生下一问。
- 让正文独立建立正确性合同、观察边界、异步完成、warm-up、同条件工作负载和分布证据的因果关系。
- 用动态图呈现文字不易同时观察的时间、状态和样本分布，并保证暂停、单步与 reduced-motion 可用。
- 形成一份可重算的最小 benchmark 协议和事件记录，使模拟证据、真实硬件证据与结论范围能够明确区分。
- 让第 00 章自然引向第 01 章：当完成事件继续被拆开时，学习者需要理解一次请求内部究竟发生了什么。

**Non-Goals:**

- 不在本章系统讲解开放环、闭环、并发调度、goodput 或生产 SLO；这些属于第 08 章及相关前置章节。
- 不实现真实模型引擎、GPU kernel、跨框架跑分或宣称某个框架更快。
- 不把设备专用环境设为阅读和完成正文的前提，也不让模拟事件冒充真实 GPU 测量。
- 不建立账号、学习进度、后端持久化或通用 benchmark 平台。
- 不重写已经验收的第 01 章，只调整课程入口和前后章导航所需的最小连接。

## Decisions

### 1. 用一次主张审查代替指标目录

整章保持 A/B 两个实现和同一项“快了 30%”的主张。正文不是依次定义 correctness、latency、warm-up、percentile，而是让主张经历五次审查：

1. `快了 30%，但做的是同一件事吗？`——先建立任务与输出接受条件。
2. `秒表从谁的世界开始？`——从不同观察者推导起止事件。
3. `函数返回，工作真的结束了吗？`——用异步反例拆开提交与完成。
4. `第一次为什么总不一样？`——把冷启动和稳态分成两个问题。
5. `一个数字如何成为证据？`——补齐同条件上下文、原始样本、分布和结论边界。

标题只在认知任务发生变化时出现。术语解释、工程设计和图示嵌在对应矛盾之后，不再额外增加“原理”“工程视角”“最佳实践”等重复标题。最终协议是前面各次修正的汇总，不能先作为清单展示。

替代方案是按 benchmark 概念逐项编排，写作和检索更容易，但会重现用户指出的 PPT 式碎片化，并使学习者只记规则而不知道规则在防止什么错误，因此不采用。

### 2. 第 00 章采用黑盒事件词汇并控制与后续章节的边界

贯穿案例只要求识别这些最小事件：客户端开始、服务端接收、主机提交、设备完成、结果可读和请求结束。正文在首次出现时解释“主机”“设备”“异步”和“完成事件”，不预设生成阶段术语。

并发数、到达模式和请求形状只作为必须声明或固定的工作负载字段，不在这里推导排队、连续批处理和压测模型。分位数只通过排序后的少量样本解释“不能只看平均值”，不展开统计课程。第 01 章负责拆开单请求内部，第 08 章负责把事件扩展为负载与服务指标体系。

### 3. 正文和视觉共同使用一份确定性案例数据

贯穿案例使用一组小而可手算的确定性事件与运行样本。正文中的数值、图示标签、事件记录和综合题从同一份领域数据生成或由测试校验，避免静态文案与动画状态漂移。建议的数据边界为：

- `BenchmarkRun`：实现、输入/输出工作量、运行序号、cold/warm 标志、成功或失败、原始事件。
- `BenchmarkEvent`：运行标识、观察者、事件名称、单调时间和可选元数据。
- `MeasurementWindow`：起始事件、结束事件、观察者与由事件差值计算的持续时间。
- `BenchmarkProtocol`：任务接受条件、环境、工作负载、warm-up 规则、指标定义和聚合规则。

领域数据不需要在首批实现中成为通用库；只有正文、图示和实践确实共享的计算才进入纯 TypeScript 模块。任何派生耗时都从原始事件计算，测试覆盖缺失事件、事件逆序和不可比较样本。

### 4. 四类动态图各自回答一个不可静态观察的问题

视觉设计采用连续的“证据工作台”语言，而不是复刻第 01 章的请求脉冲或卡片组：事件轨道、计时夹具、运行胶片和分布刻度共享有限的颜色语义，但布局随问题变化。

- **观察边界尺**：在同一事件轴上切换客户端、服务端和设备计时窗口，显示改变观察者后哪些区间进入数字。
- **主机/设备双轨图**：单步推进提交返回和设备完成，突出错误结束点仍留下的在途工作。
- **运行序列胶片**：逐次显示一次性成本何时出现，允许分别查看冷启动问题、稳态问题和未经说明的删样本行为。
- **样本分布刻度**：让 A/B 出现“中心更好而尾部更差”的反例，切换汇总方式时始终保留原始点。

所有图示先由正文建立问题，再出现控制；默认运动不携带唯一信息，暂停与单步始终可达，系统开启 reduced-motion 时改为离散状态。窄屏下事件轴允许内部横向查看或转为纵向时间序列，标题和关键标签不得被裁切或与背景失去对比。

替代方案是做一个大型自由探索 benchmark 仪表盘，但它会在概念形成前同时暴露过多变量，也会让交互取代叙事，因此拆成四次受控观察。

### 5. 保留一个要求学习者重建窗口的短实践

实现顺序仍然先完成拿掉全部交互实践也能成立的正文和四类解释性图示。随后保留一个可移植、确定性的计时窗口推演：学习者先预测错误计时会漏掉什么，再自行选择起止事件、处理缺失完成事件，并查看原始记录和派生耗时。

这项实践与双轨图的作用不同：图示负责让既定错误可见，实践要求学习者从未命名的事件中重建测量合同，并拒绝对不完整记录计算貌似精确的结果。它位于完整正文之后，不命名为独立 Lab，也不引入正文之外的新机制。真实 GPU 观察只规定同一事件格式、所需同步声明和证据标签，不提供预制性能答案或设备专用示例。

这项决定保留了“从事件重建指标”的认识增量，同时避免为了统一章节模板扩张为编码 Lab。

### 6. 章节验收采用新的缺陷报告而非复述贯穿案例

章末给出一份新的优化报告，其中混有输出工作量不一致、计时停在提交返回、选择性删除慢样本等问题。学习者要先找出使结论立即失效的缺口，再设计最小修复协议，最后写一段证据范围受限的结论。

反馈维度为：任务合同、事件边界、工作负载/环境、原始证据和结论范围。系统不因滚动到底、点击动画或运行候选实践而判断掌握。该验收测试的是迁移能力，并避免把正文各段改写成逐题背诵。

### 7. 路由和课程入口把第 00 章设为推荐起点但保留直达第 01 章

新增稳定的第 00 章路由，首页按 00、01 顺序呈现，并在两章之间提供明确的前后章关系。第 01 章现有 URL 和内容保持可用，已有链接不会失效。README 的当前内容和启动说明同步更新为两个可查看章节。

## Risks / Trade-offs

- **第 00 章概念过多，重新变成规则清单** → 始终用同一主张和有限的五次审查组织正文；删除不能推动下一问的提示框、总结标题和术语旁支。
- **与第 08 章指标教学重复** → 本章只建立单次/少量对照的证据底线；多请求负载、排队、goodput 与 SLO 留给第 08 章，并在正文明确这条边界。
- **动画提高观感却不提高理解** → 每个图先写下唯一认知问题和静态退化形式；验收时移除动画复读正文，若知识链断裂则补正文，若动画没有新观察则删图。
- **模拟异步轨迹被误读为 GPU 实测** → 数据和界面持续标注 `simulated` / `measured` 证据来源，结论模板禁止跨越来源边界。
- **共享数据模型过早抽象** → 先以第 00 章需要的最小事件类型实现；不为了未来压测平台建立插件、存储或框架适配层。
- **正文长度增加后再次显得密集** → 通过算例、短表、事件图和段落节奏分担信息，但标题数量由认知转折决定，不用卡片拆碎连续论证。

## Migration Plan

1. 新增第 00 章内容载体和路由，保持第 01 章原路由与测试通过。
2. 完成无独立实践版本的正文、来源记录和确定性案例数据，先进行连续阅读评审。
3. 逐个接入四类图示并验证键盘、暂停、单步、reduced-motion、窄屏和对比度。
4. 接入短计时窗口推演，复查它是否确实要求主动重建合同；若验收发现只是在复读图示，则在同一任务组内删去而不以完成组件为理由保留。
5. 接入综合验收、首页/README 导航和全量检查；每个可独立验收的任务组单独提交。

改动只新增章节并扩展导航，无持久数据迁移。若新路由或内容加载出现回归，可以撤回第 00 章入口而不影响已验收的第 01 章。

## Resolved Scope Decisions

- 第 00 章只交付真实 GPU 观察所需的协议字段、同步声明与证据边界，不附带设备专用示例。这样可以在没有特定硬件时完成共同主线，也不会用未经当前环境验证的代码暗示性能结论；真实设备实现留给第 09 章或后续单独变更。
- 综合验收沿用当前无后端、无掌握记录的自查模式，但改成有顺序的“先选择首个致命缺口，再写修复协议与有边界结论”。首项可以用结构化选择即时反馈判断审查优先级，后两项使用可展开检查标准支持自由解释；不新增自动评价自由文本的伪精确判分。
