## Context

第 02 章留下"下一次执行该选谁"，第 03 章让 KV 成为有所有权的状态，第 04 章把布局变成块池并留下"最后一个空闲块给谁"。第 05 章把这些输入组装成一个可推导的调度循环，见 `proposal.md` 与 `specs/continuous-scheduling-chapter/spec.md`。

现有站点使用 MDX 承载连续正文，第 00—04 章的持续约束继续有效：正文在隐藏图示与实践后仍须成立；图示不用装饰动画替代因果解释；确定性逻辑步不能冒充真实耗时。本章会接触 continuous batching 与 iteration-level scheduling 等真实机制：机制名称只在推导之后出现，其出处回到 Orca 论文；vLLM 引擎循环仅以锁定版本作实现示例。

## Goals / Non-Goals

**Goals:**

- 把执行边界形式化为决定点：每份设备工作完成后、下一份提交前，服务重新回答"这一拍执行谁"。
- 用合同定义可运行集合：到达且输入就绪、phase 已知、按第 04 章规则获得块、不在途、未结束；不可运行要分原因登记。
- 让成员资格每拍重组：晚到请求当拍加入、完成请求当拍离开，decode 组成员各贡献 1 个有效 token，由此命名连续批处理。
- 用同一工作量呈现 prefill 与 decode 对同一拍的竞争：两种策略的完整时间线手算可复核，等待的迁移而非消失是结论。
- 收束为调度合同清单并把容量压力留给下一章；两种策略都不写成最佳答案。

**Non-Goals:**

- 不实现真实调度器、抢占、chunked prefill、优先级、公平性算法或并发安全队列。
- 不把逻辑拍换算为延迟、吞吐、TTFT/ITL 或利用率；那些是第 00 章测量合同与后续指标章节的事。
- 不在本章比较真实框架调度器的默认参数；实现示例只作结构印证。
- 不改动第 00—04 章已验收的内容、模型与数字。

## Decisions

### 1. 从第 02 章的封闭决定点开始，而不是从机制名称开始

正文先复述：静态 batch 在成批那一刻冻结了成员资格，此后每个执行边界实际上不再做选择。把这一点翻转过来：执行边界本来就是决定点，静态 batch 只是"每次都沿用上次答案"的特例。于是问题变成两问：这一拍可以执行谁（可运行集合），以及从里面选谁（策略）。机制名称（连续批处理、iteration-level scheduling）在这两个问题被回答之后才出现。

替代方案是开篇介绍 continuous batching 的收益。它更快进入实现，但学习者无法回答成员资格何时改变、准入由什么决定、策略在交换什么，因此不采用。

### 2. 教学参数完全延续，调度轨迹新增两种策略

模型、请求与块池照旧：128 bytes/token、`R-long`（6+4）、`R-short`（2+1）、`R-late`（4+2）、6 块 × 4 unit。新增调度轨迹的规则：每拍至多一份设备工作；拍内顺序为到达与准入检查 → 计算可运行集合 → 按策略选择 → 执行 → 完成者释放块。准入按第 04 章规则：prompt+1 个 token 需要的块数不超过空闲块。decode 组把所有可 decode 成员合为一次执行，每人 1 个有效 token，无 padding；prefill 一次执行一个新请求。

两种策略：**prefill 优先**（新请求的 prefill 先于 decode 组，FIFO）与 **decode 优先**（decode 组先于等待中的 prefill）。固定工作量下的手算结局：prefill 优先 6 拍完成，`R-short`/`R-late` 首执行拍为 1/3；decode 优先 7 拍，首执行拍 4/5——晚到者与在跑者的等待此消彼长，没有免费方向。

### 3. 一套领域模型生成双策略轨迹并与封闭批次对照

新增 `src/learning/scheduleTrace.ts`：

- `SchedulePolicy`、`ScheduleGroup`（拍、类型 prefill/decode、成员与有效 token）。
- `ScheduleEvent`：到达、准入通过、等待块、prefill 执行、decode 执行、完成、块释放及其拍数。
- `ScheduleTickSnapshot`：每请求的可运行状态（未到达 / 待 prefill / 等待块 / 可运行 / 已完成）、持有块数、缓存 token、本拍选择。
- 纯函数生成双策略轨迹；校验器检查每拍至多一份工作、组成员拍前可运行、准入不超池、每请求恰有一次终结、prefill 按到达序。
- 对照纯函数并列第 02 章封闭批次轨迹（复用 `buildStrategyTrace('static-batch')`）与两种新策略的首执行拍 / 完成拍 / 等待拍数。正文、图与实践消费同一结果；字段名禁止出现耗时与利用率语义。

### 4. 连续正文只在五次认知任务变化时分段

1. **执行边界是一个决定点**：翻转静态 batch 的冻结成员资格；拍与决定点形式化。
2. **可运行集合由合同定义**：六项输入逐条登记，不可运行分原因；集合每拍重算。
3. **成员每拍重组，批次不再封闭**：`R-late` 当拍加入、`R-short` 当拍离开；decode 组等宽无 padding；**连续批处理**命名并对照封闭批次。
4. **prefill 与 decode 竞争同一拍**：两种策略的完整时间线手算表；等待在晚到者与在跑者之间迁移；拍数不是延迟。
5. **调度需要合同，而不是默认值**：合同清单（拍节奏、可运行定义、选择规则、准入上限）；容量压力与公平性留给后续；实现示例仅作印证。

分节标题只对应认知任务变化；不设"原理""工程视角""优缺点""小结"。

### 5. 两张图分别回答集合重组与时间线对照

第一张"可运行集合怎样每拍重组"图：以逐拍账本展示某一拍的到达/准入行、三个请求的状态芯片、被选中的执行与等待队列；策略可切换，状态由轨迹驱动。第二张"同一份工作量的三种时间线"图：以请求生命周期泳道（等待首执行 → 生成中 → 完成）沿拍轴并列封闭批次、prefill 优先、decode 优先三种组织，直观呈现首执行拍与总拍数差异。两图沿用暂停、前后单步、重置、键盘、reduced-motion、窄屏内部滚动与文字/图案双编码。

替代方案是可配置策略与请求的通用调度模拟器；它会把推导降格为参数试玩并暗示存在最优策略，因此不采用。

### 6. 实践经过 prose-only 评审，迁移验收固定存在

候选实践提供一份未解释的逐拍账本（新请求工作量与新块池，准入至少一次真正等待块），学习者先判断首个等待的原因，再重建一拍的合法顺序（到达检查 → 准入 → 可运行集合 → 选择 → 执行 → 完成释放）。迁移评估换用不同的策略、请求长度与更小的池，先检查一个致命理解错误（如把等待块当作调度选择、把拍数当延迟），再覆盖决定点、可运行合同、成员重组、竞争权衡、证据边界与待解问题六个维度。不自动评分、不写持久状态、不以背诵术语为完成证据。

## Risks / Trade-offs

- **"每拍一份工作"过度简化** → 正文明确这是教学抽象：真实系统一次执行可混合 prefill/decode（如 chunked prefill），留作后续与实现示例；不声称真实引擎每拍只做一件事。
- **拍数被误读为延迟** → 全文把拍定义为离散事件刻度，对照只数拍与等待，出现"延迟/吞吐"字样处一律指向测量边界。
- **策略写成有好坏** → 两种策略的对照表并列等待迁移方向，结论是"合同与权衡"，不给推荐。
- **准入与调度纠缠过深** → 本章准入只作可运行集合的一项输入；压力下的准入策略整体留给第 06 章。
- **对照数字漂移** → 三种组织的时间线全部来自同一纯函数族，测试从原始 fixture 独立复算首执行拍与完成拍。
