## Why

第 03 章把两种连续 KV 布局逼到失败后，留下一个问题：token 的逻辑顺序必须连续，但物理存储是否必须是单一连续区间？同时留下四条任何替代布局必须保住的合同——逻辑位置到存储位置的映射、按步追加、在途读取依赖权威状态、请求独立的终结与回收。若直接把 vLLM 的 block pool 当作框架技巧介绍，学习者会背下数据结构，而没有经历“约束怎样把固定块、块表与块池一步步逼出来”的推导。

## What Changes

- 新增第 04 章“分页 KV 怎样被逼出来”：从第 03 章四条合同出发，先检查“把一个区间拆成几段”是否保住语义、是否消除被迫搬迁，再让变长分段的空位匹配失败推导出固定块，由固定块推导出块表与块池。
- 沿用第 03 章固定模型（128 bytes/token）、`R-long`/`R-short`/`R-late` 与 24 token unit 物理池，将其划分为 4-unit 固定块；三请求完成态恰好需要 3/1/2 个块，块内追加、整块回收与空块复用让第 03 章 step 1 的外部碎片场景得到第三种结局。
- 块大小只作为“内部浪费 ↔ 映射规模”的计数对照（B=1、2、4、8、24 手算表项与浪费 unit），不换算成任何真实查找或 kernel 成本；真实系统的块实现只作版本锁定的实现示例。
- 章节止于块池仍未解决的问题：共享池的准入与调度、前缀共享、copy-on-write 与 kernel 访问模式，为后续章节建立需求；不把某个 block size 或分配算法写成最佳实践。
- 不在本章实现真实 block allocator、paged attention kernel、prefix cache、抢占、量化 KV 或真实显存性能比较。

## Capabilities

### New Capabilities

- `paged-kv-chapter`: 规定第 04 章如何从第 03 章的布局合同推导离散分段、固定块、块表与块池，并在同一物理池上与连续方案对照验收。

### Modified Capabilities

无。
