# kv-state-chapter Specification

## Purpose
规定第 03 章如何从自回归 Attention 对历史 K/V 的依赖推导 KV cache 的语义、容量账本和请求生命周期，并让连续预留与连续扩容在可复核的多请求轨迹中暴露失败，为后续物理布局解耦建立问题合同。

## Requirements

### Requirement: KV cache 由下一 token 的历史依赖推导
章节 SHALL 从第 01 章同一请求的下一次 decode 开始，先重建当前 query 为什么仍需全部历史 key/value，再引出缓存；正文 MUST 区分需要跨步保留的 K/V 与当前步产生后即可消费的 query、中间注意力分数和 logits，不得以术语定义代替依赖推导。

#### Scenario: 生成一个新的 decode token
- **WHEN** 学习者沿同一请求从长度 n 推进到 n+1
- **THEN** 能够指出哪些历史张量会被本步读取、哪些新状态会被追加，以及不保存 K/V 时必须重复计算什么

### Requirement: 缓存复用不改变 Attention 语义
章节 SHALL 以无缓存重算作为语义基线，再说明缓存历史 K/V 只改变计算复用与状态保存，不改变 token 因果可见范围。正文 MUST 说明缓存命中成立所依赖的模型层、位置、请求上下文和数值表示一致性。

#### Scenario: 比较缓存与无缓存的同一步输出
- **WHEN** 两条路径使用相同模型、token 历史、位置和采样前 logits 边界
- **THEN** 学习者能够解释两者应复用或重算哪些量，并把输出差异视为需要诊断的正确性问题而非缓存的固有效果

### Requirement: KV 容量由可复核的维度账本建立
章节 SHALL 从 dtype 字节数、层数、KV head 数、head dimension、K/V 两份状态和 token 数推导 KV 字节数，并分别展示每 token、每请求与多请求合计。公式 MUST 区分 KV head 与 query head，且 MUST NOT 把权重、短生命周期激活、工作区或 allocator 元数据计入有效 KV。

#### Scenario: 模型采用 grouped-query attention
- **WHEN** query head 数多于 KV head 数
- **THEN** 账本使用 KV head 数计算缓存，并能从原始维度重建结果而不是套用与模型不符的每 token 常数

### Requirement: 固定请求轨迹同时呈现逻辑增长与资源所有权
章节 SHALL 延续至少三个具有不同 prompt 和输出长度的请求，在每个逻辑步记录请求 phase、已缓存 token、有效 KV 字节、保留容量、物理区间、在途读取和释放许可。请求结束、取消或失败时 MUST 独立裁决其 KV 所有权，不得因共享执行组而合并释放。

#### Scenario: 短请求先于长请求结束
- **WHEN** 同时存在的短请求完成而长请求仍在 decode
- **THEN** 轨迹显示短请求停止增长，并只在其在途读取结束后释放一次自身区间，其他请求的逻辑位置和所有权保持不变

### Requirement: 最大长度预留先作为合理基线
章节 SHALL 先说明按请求最大上下文长度一次预留为何能提供稳定地址、简单边界检查和无需搬迁的增长，再用实际长度未知与并发容量限制推导过度预留。正文 MUST 区分可寻址的保留容量、已经写入的有效 KV 与尚未使用的预留空间。

#### Scenario: 多个短请求各自声明很大的最大长度
- **WHEN** allocator 为每个请求按上限保留连续区间而实际生成很短
- **THEN** 学习者能够从账本分别算出有效、保留未用和剩余可分配容量，并解释准入失败为何不等于有效 KV 已耗尽显存

### Requirement: 按需连续扩容暴露搬迁合同
章节 SHALL 认真分析只按当前长度分配并在容量不足时扩展连续区间的方案，说明原地扩展、另址分配加复制和拒绝增长分别需要满足什么条件。搬迁分析 MUST 纳入旧区间、新区间、复制期间峰值、在途设备读取、地址发布和失败回滚，不得把扩容写成无代价数组操作。

#### Scenario: 请求尾部没有足够相邻空间
- **WHEN** 一个仍在 decode 的请求必须增长且后方区间已被其他请求占用
- **THEN** 学习者能够重建另址分配与复制的合法顺序，并指出旧地址在所有读取者切换前为何不能释放

### Requirement: 容量不足必须区分有效占用、预留、峰值与碎片
章节 SHALL 使用同一物理池轨迹分别标记有效 KV、保留未用、搬迁双份存活、空闲区间和不可满足的连续申请。OOM 或准入拒绝结论 MUST 回到原始区间与请求事件，且 MUST NOT 仅凭总空闲字节或模拟逻辑步声称真实 GPU 性能。

#### Scenario: 总空闲容量足够但没有足够大的连续区间
- **WHEN** 新请求的连续申请大于任一空闲区间而小于空闲字节总和
- **THEN** 学习者能够把失败归因为外部碎片，并与有效 KV 过大、最大预留过多和搬迁峰值分别处理

### Requirement: 图示只承担张量复用与内存演化观察
章节 SHALL 只为历史 K/V 被下一步读取、请求容量增长和物理区间搬迁等静态文字难以观察的状态加入图示，并提供暂停、单步、键盘、窄屏和 reduced-motion 支持。图示 MUST 保留原始维度或区间读数，且移除任一图后正文结论仍然完整。

#### Scenario: 单步观察一次连续扩容
- **WHEN** 学习者推进到申请新区间、复制、发布新地址和释放旧区间
- **THEN** 页面只更新当前原子事件相关的所有权与区间状态，历史记录保持可复核，颜色不是唯一编码

### Requirement: 章节止于逻辑连续与物理连续的冲突
章节 SHALL 从最大预留和连续扩容共同暴露的约束形成下一问：token 的逻辑顺序必须连续，但其物理存储是否必须是单一连续区间。章节 MUST 将 block、page、block table、paged attention、共享前缀与生产回收算法留给后续章节。

#### Scenario: 学习者走到章节结尾
- **WHEN** 两种连续分配方案均由同一请求与物理池轨迹展示失败
- **THEN** 学习者能够写出下一种布局必须保持的逻辑索引、读取、所有权和回收合同，但不会把分页实现当作本章已经证明的唯一答案

### Requirement: 章节验收要求迁移容量诊断
章节 SHALL 使用不同于正文的模型配置、请求长度与物理区间轨迹，检查学习者能否重建 KV 字节账本、识别首个容量失败、保护在途读取并限定结论。验收 MUST NOT 以背诵公式、播放动画、运行示例或说出“paged KV”作为完成证据。

#### Scenario: 新轨迹同时包含 GQA、扩容与请求取消
- **WHEN** 学习者审查新的模型维度和连续内存事件
- **THEN** 反馈分别检查依赖语义、字节计算、容量归因、搬迁/释放顺序、证据边界与待解物理布局问题
