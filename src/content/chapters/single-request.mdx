先从一个看起来没有系统问题的调用开始。客户端提交一段文本，要求模型生成不超过 8 个 token，遇到结束 token 就停止，并希望服务端边生成边返回。为了让后面的变化都能对照，我们固定同一个请求 R：输入经过一个假想 tokenizer 后得到 `x1, x2, x3, x4`，模型随后选择 `y1, y2, y3, <eos>`。这些符号只表示词表编号和位置关系；它们不暗示一个 token 恰好对应一个汉字或单词，也不冒充任何真实模型的输出。

从客户端看，合同很短：输入文本和生成参数进去，若请求成功，文本片段和结束原因出来。但服务端若只保存这份合同，甚至还不知道该做几次计算。请求 R 可能在第一个输出后命中停止串，也可能生成满 8 个 token；客户端还可能在两者之间断开。一次调用的边界由 API 给出，计算的边界却必须从模型的依赖关系里推出来。

<h2 id="one-call-many-steps">一次调用，多次执行</h2>

一个自然的旧模型是：调用一次模型，模型像普通函数那样直接返回完整答案。这个模型对分类器很合适——一次前向计算得到类别分数，选出类别，请求就完成了。文本生成不同，因为模型并不直接预测整段未知文本，而是给出“在已有序列之后，下一个 token 是什么”的分布。

这里的 **token** 是模型词表中的离散编号。tokenizer 负责在文本和编号序列之间转换，切分规则属于具体 tokenizer；所以字符数、单词数、token 数和网络发送片段数都不能互换。模型真正消费的是 `x1…x4` 这样的编号序列，而不是接口里的原始字符串。

“下一个”带来了关键依赖。若已经知道前缀 `x1…x4`，模型可以计算第一个输出的分布：

```text
P(y1 | x1, x2, x3, x4)
```

但在 `y1` 尚未选出前，第二个输出所需的条件还不存在：

```text
P(y2 | x1, x2, x3, x4, y1)
```

这种把序列概率拆成一连串条件概率、让后一个位置依赖此前结果的生成方式叫作 **自回归**。它不是推理框架添加的流程，而是模型生成语义施加的顺序约束。即使有无限计算资源，也不能在不知道 `y1` 的情况下精确执行依赖 `y1` 的那一步。

于是“一次请求就是一次模型前向”的旧模型失效了。对 R，服务端至少要经历这样的逻辑过程：用完整 prompt 得到 `y1` 的候选分数，选出 `y1`；把 `y1` 纳入前缀，再得到 `y2`；继续到 `y3`，最后选到 `<eos>`。这里每一次依据当前前缀产生下一位置候选分数的模型调用，才是一次 **forward**；从一次 forward 的结果选出一个 token 并更新请求，则构成一个 **生成步**。API 请求包住多个生成步，每个生成步通常包含一次模型执行，却还包含模型以外的决策。

这个区分立即影响接口设计。请求的 `max_new_tokens=8` 约束的是最多完成多少个生成步，不是再发 8 次 API；结束 token 是词表中的一个候选，不是模型进程退出；客户端取消终止的是请求剩余工作，不等于已经发出的设备计算能够在任意指令处消失。我们尚未讨论如何实现这些边界，但已经知道一个只接受文本、同步返回完整文本的内部函数会隐藏后续必须处理的状态。

<h2 id="two-shapes">同一循环的两种形状</h2>

如果所有输出都顺序产生，为什么推理系统还要区分两个执行阶段？答案不在阶段名称里，而在“哪些位置已经知道”。

Transformer 的每一层会让一个位置读取其他位置的信息。对生成模型使用的 **causal Attention**，位置只能读取自己和它之前的位置，不能偷看未来。可以把每个位置产生的信息简化成三类向量：query 表示当前位置要找什么，key 表示历史位置能用什么被匹配，value 表示匹配后取回什么。真实计算还有多层、多头、位置编码和投影；本章只保留解释执行形状所需的依赖。

R 到达时，`x1…x4` 已经全部确定。虽然 `x4` 依赖前三个位置，`x3` 不能读取 `x4`，但四个位置的依赖图都已知；因果遮罩负责屏蔽非法方向，硬件可以在一次模型执行中并行处理这四个位置。若 batch size 为 1、隐藏维度为 `d`、词表大小为 `V`，逻辑输入形状可写成 `[1, 4, d]`，逻辑 logits 形状可写成 `[1, 4, V]`。生成只需要最后位置那一行分数来选择 `y1`，但各 prompt 位置的中间结果都参与建立上下文。

这个“用完整已知 prompt 填充模型状态，并产生首个输出分布”的阶段后来才有名字：**prefill**。先看依赖再记名字很重要，因为 prefill 不是另一个模型，也不意味着一次得到所有输出；它只是同一组模型权重面对长度为 4 的已知输入。

选出 `y1` 后，情况发生了变化。历史位置的 key 和 value 与上一步完全相同，新增的只有 `y1` 所在位置。最朴素的实现可以把 `x1…x4,y1` 全部重新送入模型，结果在语义上正确，却会重复计算四个历史位置。如果保留每层已经产生的 key/value，下一步只需为 `y1` 计算新的一份 query、key 和 value，让新 query 读取由五个位置组成的 key/value 历史，再产生 `y2` 的 logits。

这份跨步保留的历史通常称为 **KV cache** 或 KV state。称它为 cache 容易让人误以为它随时可丢：丢掉后确实可以从全部 token 重算，因此它不是语义真相的唯一副本；但在正常增量执行中，下一步直接依赖它，重算又有实际成本，所以服务系统必须把它当作由请求占有、会增长、终止时必须释放的资源。如何分配它、是否分页以及多个请求怎样竞争容量，留给后续章节。

每次只消费一个新增 token、读取已有 KV、追加一个位置并产生下一 token 分布的阶段叫作 **decode**。它的逻辑输入从 `[1, 4, d]` 变成 `[1, 1, d]`，Attention 却要读取长度为 5、6、7……的历史。下面的轨迹把名字背后的变化摊开：

| 执行 | 本次新增输入 | 执行前 KV 长度 | 本次产生的分布用于选择 | 执行后 KV 长度 |
| --- | --- | ---: | --- | ---: |
| prefill | `x1…x4` | 0 | `y1` | 4 |
| decode 1 | `y1` | 4 | `y2` | 5 |
| decode 2 | `y2` | 5 | `y3` | 6 |
| decode 3 | `y3` | 6 | `<eos>` | 7 |

注意最后一行：模型选择了 `<eos>`，但通常无需再把 `<eos>` 送入下一次 forward，因为停止判断会阻止下一步。于是生成了 4 个输出 token，KV 只需要记录 prompt 和前三个、确实作为后续输入使用的输出位置。若某个实现为了别的合同处理结束 token，状态长度可能不同；必须以“哪些 token 真正进入过模型”解释，而不能靠阶段名猜测。

prefill 和 decode 因而共享权重、层结构和“给定前缀预测下一 token”的语义，却有不同执行形状。prefill 的多个已知位置具有位置级并行性；decode 步之间受自回归依赖约束，每步只有一个新增位置，同时读取不断增长的历史。至于两者在某张 GPU 上谁耗时更多、瓶颈属于计算还是内存，不能仅由这张形状表宣布，需要在固定模型、长度、batch 和硬件后测量。

<h2 id="visible-output">生成不等于可见</h2>

到目前为止，我们故意把“模型产生 `y1`”说得很简略。模型实际输出的是长度为 `V` 的 **logits**：词表中每个候选 token 的未归一化分数。logits 既不是被选中的 token，也不是文本。生成策略先按温度、候选截断、禁用词或重复约束等规则变换分布，再用贪心或随机采样选出一个编号。同一组模型权重和同一前缀可以配合不同策略，因此 sampling 属于生成控制流，而不是模型 forward 的同义词。

选出编号后仍不能无条件发送。服务端至少要回答三个问题：它是否命中 `<eos>`、长度上限或用户停止串；增量 tokenizer 解码现在是否形成了可安全提交的文本；在提交的一刻，请求是否仍允许输出。某些 token 只是子词或字节片段，单个 token 未必对应一个可独立显示的 Unicode 字符；文本停止串也可能跨两个 token，增量解码器和停止检测器因而需要保留少量尾部状态。

对 R，可以把事件分成四条同时推进但不能混写的记录：

| 时刻 | 模型与生成决策 | 请求内状态 | 客户端可见 | 资源状态 |
| --- | --- | --- | --- | --- |
| `t0` | prompt 尚未执行 | 保存参数与 `x1…x4` | 空 | 尚无 KV |
| `t1` | prefill logits 选出 `y1` | 记录 `y1`，KV 长度 4 | 仍可能为空 | 请求持有 KV |
| `t2` | `y1` 解码为可提交片段 | 输出游标前移 | 第一个片段可见 | decode 仍需 KV |
| `t3` | 后续 decode 选出 `y2`、`y3` | 生成结果继续增长 | 片段逐次提交 | KV 继续增长 |
| `t4` | 选出 `<eos>`，不再启动 forward | 结束原因为 `eos` | 流关闭后客户端确认结束 | KV 才可进入释放 |

`t1` 到 `t2` 的距离说明首个输出 token 已经被选出，不代表客户端已经看到文字；解码缓冲、事件循环、网络写入和客户端读取都在两者之间。`t2` 又远早于 `t4`，所以“首个可见输出”“生成结束”和“资源释放”是三个边界。streaming 的含义正是服务端在请求终止前分批提交输出，它缩短可见等待，却没有让未来 token 提前存在，也没有解除 decode 步之间的依赖。

网络发送还引入服务端内部没有的失败和背压。若客户端读取很慢，发送函数可能阻塞或积累缓冲；若客户端在一个片段写入期间断开，服务端必须知道该片段是否已经越过不可撤销的提交点。最小同步执行器可以等待每次发送完成，以避免无界缓冲，但这会把慢客户端直接串进生成循环。是否拆分生成与发送、缓冲上限多大，是后续 serving 设计问题；本章先要求无论怎样拆，输出许可都必须存在一个明确、可序列化的判断点。

<h2 id="request-state">状态从哪里来</h2>

现在可以回答为什么服务端需要“请求对象”，而不能把若干局部变量随手塞进循环。下一步模型执行依赖 KV 和上一个 token；停止判断依赖已经生成的数量及文本尾部；增量解码依赖尚未提交的字节；发送依赖客户端流是否仍有效。它们的生命周期都跨越单次 forward，又必须在同一个请求终止时收束。

一个最小请求上下文至少需要以下信息。字段名是教学接口，不是框架最佳实践：

```text
RequestContext
  identity: request_id, deadline
  contract: prompt, max_new_tokens, stop_rules, sampling
  generation: prompt_ids, generated_ids, next_input_id
  model_state: phase, kv_handle, in_flight
  output_state: decoder_tail, stop_matcher, stream
  lifecycle: abort_requested, terminal_reason, cleanup_started
```

每个字段都可以回指前文约束。`generated_ids` 不是为了方便展示历史，而是停止长度和下一步输入需要它；`kv_handle` 来自避免重复计算历史位置；`decoder_tail` 来自 token 与可见字符边界不一致；`terminal_reason` 则让调用方区分正常结束、取消、超时和失败。若删掉一个字段，应当说明由谁提供等价信息，而不是仅以“实现更简洁”为理由。

执行阶段和结束原因应分开。阶段描述当前工作位于 `accepted`、`prefill`、`decode` 还是 `finalizing`；结束原因描述它为何不再继续，例如 `eos`、`length`、`stop_sequence`、`cancelled`、`timed_out` 或 `failed`。把两者做笛卡尔积会制造 `cancelled_during_prefill`、`timed_out_during_decode` 等不断增长的枚举，却仍然回答不了清理是否完成。一个更小的状态模型是：运行阶段可以进入 `finalizing`，第一个成功登记的 terminal reason 决定对外结果，完成清理后统一进入 `done`。

状态还不够，必须写出资源所有权。否则“终于进入 done”可能只意味着布尔值改了，KV、输出流或在途计算仍被遗忘。

| 资源 | 活跃期间谁持有使用权 | 何时不能立即释放 | 谁负责最终动作 |
| --- | --- | --- | --- |
| 请求上下文 | 请求执行器 | 终止回调仍在读取字段 | 生命周期管理器完成一次性销毁 |
| KV handle | 当前请求 | 设备仍有读取它的在途工作 | 模型状态适配器在安全点 `release_once` |
| 输出流 | 传输适配器，请求拥有写入许可 | 某次发送的提交结果尚未确定 | 传输适配器关闭一次并报告提交结果 |
| 执行槽/队列位置 | 当前执行策略 | 调度器仍可能选中该请求 | 所有者撤销可运行资格；单请求版本中只是一个槽 |
| 在途设备工作 | 设备运行时 | kernel 已提交但尚未到达安全点 | 运行时等待或确认完成，不能由请求直接释放其输入 |

这里故意区分“拥有对象”和“拥有使用权”。KV 内存可以由统一 allocator 真正拥有，请求只持有一个租约；但只要租约没有释放，容量账本仍应算在该请求上。输出连接可以由 Web 服务器创建，请求执行器却必须在发送前持有有效的输出许可。工程接口需要表达这些关系，而不是让垃圾回收器猜测业务终止语义。

<h2 id="termination">结束不是一个瞬间</h2>

正常路径很容易给人错误信心：选到 `<eos>`，跳出循环，释放 KV，关闭流。真实终止可能从控制流之外到达。客户端取消可以发生在 prefill 等待中、两次 decode 之间，也可以紧邻一次发送；超时只是由时钟触发的取消意图；模型执行、tokenizer 和网络各自都可能失败。它们共享同一要求：阻止新的不合法动作，让已经不可撤销的动作得到一致解释，并最终释放每项资源。

考虑 R 的 `y2` 已被选出、文本片段已准备好，而取消信号正好到达。若取消先取得生命周期的终止权，`y2` 不得再提交，执行器不启动下一次 decode，流以 `cancelled` 收束。若发送先越过传输层定义的提交点，客户端可能合法地看到 `y2`；稍后到达的取消只能阻止 `y3` 及后续工作，不能假装撤回已提交字节。这两个结果都可以正确，前提是系统规定唯一的先后判定点，并让事件记录能够解释哪一个先发生。

真正危险的是第三种含混结果：生成线程检查“未取消”，取消线程随后关闭并清理，生成线程仍把 `y2` 写进已经终止的流，最后两边各释放一次 KV。避免它不能只靠多写几个 `if cancelled`，因为检查与动作之间仍有空隙。生命周期接口需要提供类似 `emit_if_active(delta)` 和 `try_finish(reason)` 的原子语义：发送许可的取得与终止权的登记按同一顺序裁决；只有第一次 `try_finish` 改变结束原因；清理由 `release_once` 防止重复，但幂等不是忽略所有错误的借口，重复尝试仍应可观测。

下面的伪代码把前面推导出的边界组织成一个单请求执行器。它不是生产框架模板；每一行只是为已经出现的约束找一个明确位置。

```text
async execute(request):
    ctx = lifecycle.accept(request)

    try:
        ctx.throw_if_aborted_or_timed_out()
        ctx.prompt_ids = tokenizer.encode(request.prompt)

        ctx.phase = PREFILL
        step = await model.prefill(ctx.prompt_ids)
        ctx.kv_handle = step.kv_handle

        while true:
            ctx.throw_if_aborted_or_timed_out()

            token = sampler.choose(step.logits, request.sampling)
            ctx.generated_ids.append(token)
            output = output_policy.observe(
                token, ctx.generated_ids, decoder, request.stop_rules)

            # 输出许可和终止登记使用同一个生命周期顺序。
            # 若取消已经取得终止权，emit_if_active 不会提交 delta。
            if output.safe_delta is not empty:
                await ctx.emit_if_active(output.safe_delta)

            if output.stop.matched:
                ctx.try_finish(output.stop.reason)
                break

            ctx.throw_if_aborted_or_timed_out()
            ctx.phase = DECODE
            step = await model.decode(token, ctx.kv_handle)

    catch Cancelled:
        ctx.try_finish(CANCELLED)
    catch DeadlineExceeded:
        ctx.try_finish(TIMED_OUT)
    catch error:
        ctx.record(error)
        ctx.try_finish(FAILED)
    finally:
        ctx.phase = FINALIZING
        await model.wait_until_safe(ctx.in_flight)
        await ctx.release_kv_once()
        await ctx.close_stream_once()
        ctx.mark_done()
```

这段控制流需要几份比函数名更重要的接口合同。`model.prefill` 成功返回时必须同时交付可用于 sampling 的 logits 和可追踪的 KV handle；失败时必须说明是否留下了待回收资源。`model.decode` 只能在 handle 有效且没有另一项工作非法修改它时启动。`output_policy.observe` 要同时处理 token 级停止、跨 token 的文本停止和增量解码，只暴露不会把停止串前缀误发出去的 `safe_delta`。`emit_if_active` 返回后必须说明片段是否已提交，取消与发送才能被记录为确定顺序。`wait_until_safe` 不是笼统的“同步一下”，而是释放 KV 前确认没有在途工作仍会读取它。`close_stream_once` 应将对外结束原因映射到传输协议，但不得改变已经确定的内部原因。

也可以逐项反查为什么不能简单删除这些步骤。去掉 prefill 后的循环，违背自回归依赖；在 sampling 前释放 KV，下一次 decode 失去历史；先发送再判断停止，可能把应被截去的停止内容交给客户端；捕获取消后立刻释放，可能让仍在执行的设备工作读取已复用内存；只在正常分支关闭流，则失败路径把连接留给超时兜底。工程设计不是附在原理之后的一组经验，而是把每项语义约束变成状态、顺序和所有权。

这个执行器仍然刻意省略了生产系统的主要困难。它一次只服务一个请求，没有回答新请求何时进入、prefill 与 decode 如何共享设备；KV handle 只有生命周期，没有容量、碎片和布局；等待发送会受到慢客户端影响；取消只能在定义的安全点生效；设备异步和错误传播被压在一个接口后面。下一章将只改变第一个条件——让多个长短不同的请求同时到达——看看这个正确的单请求循环为何不能自然变成高效服务。KV 分配、连续调度、背压和真实 GPU 行为会在各自的矛盾出现时再展开，而不是在这里提前列成优化菜单。

在离开本章前，可以用一个判断检查推导是否真的连上了：若有人声称“请求已经返回第一个 token，所以它几乎结束了”，你应当能从剩余的自回归步骤、仍在增长的 KV、尚未确定的终止原因和未关闭的输出流四个角度指出这句话遗漏了什么。能够重建这条因果链，比记住 prefill、decode 的名称更接近后续工程工作的起点。
