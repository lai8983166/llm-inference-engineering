八章推导攒下了一整套带原因的原始事件——到达、准入、排队、执行、终态。事件本身不是结论：从事件到“系统快不快”之间隔着四层选择——定义（哪个事件对决定一个指标）、统计（均值还是分位）、负载（开环还是闭环）与口径（吞吐还是 goodput）。每层选错都会造出看起来严谨的错误结论。本章把第 00 章的测量合同带到服务尺度：指标是事件的聚合，聚合必须能走回头路。

<h2 id="event-pairs">每个指标都是事件对的差</h2>

“这个服务快不快？”——八章的答案一直是“先给事件”。现在事件有了，新的含糊出现在定义上。同一份轨迹里问“`K-d` 等了多久才拿到第一个 token"，至少有两种算法：从它**到达** t2 算到首个输出 t4，是 2 拍；从它**准入** t4 算到首个输出 t4，是 0 拍。两个数字都对，量的是两件事——前者包含 2 拍排队，后者把排队整个藏在了指标之外。哪一个是“TTFT”？取决于报告钉没钉边界。

所以定义先于数值。每个指标都钉死一对起止事件：**排队** = 准入拍减到达拍；**首 token** = 首个输出事件拍减到达拍；**间隔**（ITL）= 相邻两个输出事件拍之差；**端到端** = 终态拍减到达拍。在本章的固定工作量上逐个算：`K-a` 一路绿灯——排队 0、首 token 0、间隔 [3,2]、端到端 5；`K-d` 排队 2、首 token 2、间隔 [1]、端到端 3——它的首 token 恰好等于排队，因为这个教学策略里准入当拍就 prefill；`K-b` 在 t4 被取消，端到端 4、间隔 [2]，它是被中断的样本而不是残缺数据；`K-e` 排队中超时、从未执行，排队与首 token 记为“未定义”而不是 0——把它记成 0，均值就凭空变好了。

教学单位仍是拍。定义是事件对的差值，真实系统对时间戳做同样的差——定义可迁移，数值不可迁移，这是八章“拍不是时间”纪律的延续。真实工具同样要钉边界：某个压测工具把客户端并发限流造成的等待（`client_queue_time`）单列为独立指标，而不是混进服务延迟——因为边界不同的数字不可相加、不可比较。两份报告的首 token 对不上时，先查边界，再查数字。

<h2 id="distribution-not-mean">分布先于均值</h2>

把每人的间隔拼起来——`K-a` 的 [3,2]、`K-b` 的 [2]、`K-c` 的 [1,2]、`K-d` 与 `K-f` 各一个 1——得到间隔池：[1,1,1,2,2,2,3]。均值 12/7 ≈ 1.71 拍。这个数字回答了什么？如果每个间隔都接近 1.71，它描述一切；如果一半是 1、一半是 3，它描述不了任何一次真实体验——均值是分布的浓缩，浓缩必然丢信息，丢的恰恰是住在尾部的那部分。

分位数把尾部找回来。本章用最近邻秩：把样本排序，第 ⌈p·N⌉ 个值就是 p 分位——7 个样本的 p50 是第 4 个（2 拍），p99 是第 7 个（3 拍，小样本下 p99 就是最大值，这个退化要如实登记）。分位数的意义要靠一个反例撑起来：

| 系统 | 间隔样本 | 均值 | p99 | SLO：间隔 ≤ 4 @ p99 |
| --- | --- | ---: | ---: | --- |
| A：快时很快、偶尔卡顿 | [1,1,1,1,5] | 1.8 | 5 | **违约** |
| B：恒定稍慢 | [2,2,2,2,2] | 2.0 | 2 | **达标** |

A 的均值更好，B 的承诺兑现。选 A 还是 B，取决于服务答应过用户什么——这就是 **SLO** 的含义：阈值加分位，缺一不可。“平均间隔不超过 4”和“99% 的间隔不超过 4”是两份完全不同的合同，前者几乎总能满足，后者才逼近用户的真实体验。已发表的大规模服务分析早就指出：请求扇出到许多服务器时，整体延迟由最慢的组成者支配——用户感受到的从来不是均值。这不是说均值无用：均值回答总量问题（资源消耗、总吞吐成本），分位回答承诺问题（SLO 达成）。两者不可互相替代，报告必须带分布。

<h2 id="open-closed-loop">开放环与闭环测的不是同一件事</h2>

前八章所有 fixture 都有一个共同的隐含前提：到达时刻是预先固定的，与服务快慢无关。这叫**开放环**——负载生成器按时刻表发请求，服务再慢，请求照样到。另一种是**闭环**：客户端等上一个请求完成（或失败）再发下一个。本章的固定工作量用同一服务跑两种环：

| | 开放环 | 闭环（串行客户端） |
| --- | ---: | ---: |
| 到达拍 | 0,0,1,2,3,6（固定） | 0,3,6,9,11,15（由完成推导） |
| 最大队列深度 | 2 | 0 |
| 有人排队吗 | `K-d` 排 2 拍、`K-e` 排到超时 | 全部 0 拍 |
| 总拍数 | 8 | 17 |

闭环下排队消失了——不是服务变好了，是客户端的串行节奏把排队**吸收**了：请求永远等到系统空闲才到达。于是闭环测出的是“无排队能力”，永远测不出过载行为——你把请求数翻十倍，闭环只会把完成时刻顺延，队列恒空，指标恒好。开放环才能暴露第 06 章那种池见底的动态。真实压测工具把到达过程做成显式参数：无限速率（全部立即到达，接近闭环的极端）或有限速率按 Poisson/Gamma 过程生成，并发上限另设——参数不同，测出的数字不可互比。哪种环“正确”？取决于生产流量像哪种：交互式用户各自独立发请求接近开放环，深度轮询的批处理客户端接近闭环。**负载生成器的性质是结论的一部分**，报告必须声明它。

<h2 id="goodput">完成不等于有效</h2>

一个窗口内吞吐是多少？数终态：6 个请求全部有了终态，窗口 8 拍，吞吐 6/8。但其中 `K-b` 是被客户端取消的（生成到一半，无人接收后半），`K-e` 是排队中超时的（从未执行）。把它们也算作“服务产出”，等于把失败记成功。**goodput** 只数有效完成：终态原因为 eos 或长度上限的请求。本窗口 4 个有效完成，goodput 4/8——比吞吐整整少了四分之一，差额逐项可查：取消 1、超时 1。

这不是新口径，是第 06/07 章账本的延续。第 06 章的拒绝、第 07 章的取消、超时、断开、失败——每一种终态原因在这里进入指标的分母。一个系统可以用拒绝所有“难伺候”的请求来美化延迟分位（被拒者的等待根本不进延迟池），可以用吞吐掩盖三分之一的失败——只有 goodput 加终态原因分布能拆穿。报告口径因此固定：吞吐、goodput、排除清单（按原因）三者并列，缺一不可。真实系统里无效完成的代价还不止统计：被取消请求在取消前的每一拍执行都是白算的功，第 07 章叫它无效希望，本章给它一个度量位置。

<h2 id="aggregation-chain">聚合链要能走回头路</h2>

把本章收束成一条固定的链：**原始事件 → 每请求指标 → 分布 → SLO 判定**。逐请求指标由事件对差值算出，分布由全体取值排序得出，判定由阈值加分位给出——每一层只做一件小事，所以每一层都可以反向走：给你 p99 = 3，你能指回排序条带第 7 个值；给它一个请求名，你能沿事件流重算它的每个指标。可回溯性不是锦上添花——它是第 00 章证据链在服务尺度的形态：任何结论都能退回到原始事件，任何原始事件都能前推到它影响的结论。

由此固定报告模板：负载（环式、请求集合、到达过程）、定义（每个指标的事件对边界）、分布（含分位计算方法）、口径（吞吐与 goodput 并列、排除清单）、判定（阈值、分位、达成情况）。五项缺一，结论就退化为故事。最后留一个本章不回答的问题：指标异常了，然后呢？首 token 分位正常而间隔分位劣化，指向 decode 路径而不是准入；排队拍暴涨而服务侧指标正常，指向上游或容量——归因指向是下一章的入口，那里要拿着 profiler 进入真实系统，把“哪一层慢”变成“哪一行慢”。而无论走到多细，本章的链都是底座：没有可回溯的事件与诚实的口径，再深的 profiler 也只是在精确地测量错误的东西。
