第 02 章结束时留下的问题不只是“下一次执行选谁”：每个被选中的请求都在持续积累后续 token 仍要读取的 K/V 状态，而这套状态的容量、所有权和存放方式还没有被推演过。本章从一次 Attention 计算开始，弄清哪些量必须跨步保存、保存多少、怎样增长、何时释放，以及最朴素的连续内存方案究竟被什么约束击穿。

<h2 id="recompute-or-reuse">下一 token 又要过去的什么</h2>

从第 01 章同一请求的下一次 decode 开始：当前 token 的 query 需要与全部历史位置的 key、value 发生 Attention。先写出不保存任何历史时必须重复计算什么，再看哪些量其实是同一步计算的同一批输入——由此得到 KV cache 的语义与它的复用正确性合同。

<h2 id="kv-byte-ledger">保存 K/V 不是免费的</h2>

用一个可手算的固定模型逐项推导每 token 的 KV 字节数，再沿单 token、单请求、多请求的阶梯建立容量账本，并让三个请求的到达、增长与独立释放把 KV 变成有所有权的系统状态。

<h2 id="max-reservation">最大预留把未知变成空占</h2>

输出长度在生成前是未知的。先承认按声明上限一次预留的合理价值：地址稳定、边界检查简单、增长无需搬迁；再用请求上限与实际长度的差异暴露准入压力。

<h2 id="contiguous-growth">按需增长把空间变成搬迁</h2>

只按当前长度申请可以省下预留，但区间尾部一旦被邻居占用，增长就要走完另址申请、双份存活、复制、地址发布、等待在途读取与旧区间释放的完整链条。

<h2 id="fragmentation-wall">空闲总量够，连续空间仍不够</h2>

请求独立结束会留下孔洞。当空闲字节总和足够、却没有一段足够大的连续区间时，连续分配方案同时暴露出有效占用、过度预留、搬迁峰值与外部碎片四种不同的容量失败，也留下一个问题：逻辑上连续的 token 序列，是否必须占据连续的物理区间。
