第 02 章结束时，三个请求的执行组织被压成一句话：下一次执行该选谁。但这句话有一个没写出来的前提——被选中的请求把它的 KV 放在哪里、还放得下多少。第 01 章只给过一句承诺：请求终止时要等在途工作结束再释放 KV。现在必须把这份使用权变成可计算、可追踪的系统状态：它为什么存在、占多少字节、怎样增长、何时归谁所有。

<h2 id="recompute-or-reuse">下一 token 又要过去的什么</h2>

回到 `R-long`。prefill 之后它有了 6 个 prompt token 的历史，并且已经产出第一个输出 `y1`。生成 `y2` 的那一步，输入只有一个 token：`y1` 自己。它进入模型后，每一层先为它算出 query、key、value 三个投影；而 Attention 的定义要求这个 query 与位置 0 到 n 的每一个 key 计算分数，再对相应的 value 加权求和——n 是当前历史长度，包含刚刚算出投影的当前位置。换句话说，**当前 query 是本步的输入，历史 K/V 是本步要读的全部账**。

先看一条不做任何保存的路径。为了这一步的 Attention 能拿到位置 0…n 的 K/V，把整段 token 历史重新送进模型，逐层重新计算所有位置的投影，用完即抛；下一步生成 `y3` 时，再把 0…n+1 全部重算一遍。注意这条路径并没有算错任何东西：同一批输入、同一组权重、同一层，重算出来的就是同一批 K/V。

再看第二条路径。历史位置的 K/V 上一步已经算过，而且没有谁会修改它们——推理时权重冻结，token 历史一旦确定也不再变。那就把它们存起来：本步只计算当前 token 的 K/V 并追加进去，然后做同一次 Attention。两条路径的语义完全等价：token 的因果可见范围相同，每一对 query 与 key 的计算相同。区别只在于，重算把这份计算结果当作即抛的中间量，第二条路径把它当作跨步保存的状态。

到这里才有理由给这批状态命名：**KV cache**——按请求、按层、按位置保存的 key、value 投影，供后续每个 token 的 Attention 读取。

不是所有量都值得这样保存。本步的 query、注意力分数、加权得到的 context 向量、logits，都是本步产生、本步消费，下一个 token 不再读它们；留下来只会占用空间。判断什么成为状态的标准不是它有多大，而是后面的步骤还读不读它。按这个标准，跨步要读的只有历史 K/V，要追加的只有当前 token 的 K/V。

复用有一个比“省计算”更重要的前提：缓存命中成立的条件是同一模型、同一层、同一请求、同一位置编码、同一数值表示。换一层，投影不同；换一个请求，token 历史不同；位置错位，注意力对错了地方；数值表示改变，保存的字节就不再是重算会得到的字节。任何一条被破坏，读到的就不是本应重算出的那批 K/V，输出会随之改变。所以缓存复用出问题不是性能退化，是正确性缺陷，要按缺陷去诊断，而不是当作缓存固有的代价。这份合同也正是第 01、02 章反复写“KV 使用权”的原因：请求读写的是自己的 KV cache；别的请求结束、取消或失败，都不构成动它的理由。

还有一条证据边界要先立起来：复用省下的是重复计算，本章不把“省”换算成任何时间或吞吐数字——那需要回到第 00 章的测量合同，在固定软硬件上测。

<h2 id="kv-byte-ledger">保存 K/V 不是免费的</h2>

把“要保存”变成“占多少”，需要一本可以逐项复算的账。本章固定一个可手算的教学模型：4 层；每层 Attention 有 8 个 query heads、2 个 KV heads，head dimension 是 4；数值表示每元素 2 bytes。对每一个 token、每一层，要保存的是：

```text
4 layers × 2 (K,V) × 2 KV heads × 4 dim × 2 bytes = 128 bytes
```

逐项看：每层有 K 和 V 两份；每份属于 2 个 KV heads 之一；每个 head 是 4 维向量；每个元素 2 bytes；一共 4 层。8 个 query heads 不进入这条公式——query 属于当前步，算完即抛，决定缓存大小的是 KV heads 的数量。8 个 query heads 共享 2 个 KV heads，这是分组查询结构（GQA）的形状；真实模型经常如此，所以“按参数规模估缓存”或“把 query head 数代进去”都会算错。要核对一个真实模型，应该读它配置里的层数、KV head 数、head 维度与 dtype 字段，再套同一条公式。

单请求的账沿生成过程积累。本章约定：每个被模型处理过的 token 都留下 K/V，包括最后生成的输出 token。于是完成态缓存恰好是 prompt 加输出：`R-long` 是 6 + 4 = 10 个 token，`R-short` 是 2 + 1 = 3，`R-late` 是 4 + 2 = 6。把一个 token 的 KV 记作一个 **token unit**，三个请求完成时的有效 KV 是：

| 请求 | prompt | 输出 | 完成态缓存 | 有效 KV |
| --- | ---: | ---: | ---: | ---: |
| `R-long` | 6 | 4 | 10 units | 1280 bytes |
| `R-short` | 2 | 1 | 3 units | 384 bytes |
| `R-late` | 4 | 2 | 6 units | 768 bytes |

这本账只数 K/V 本身。模型权重、当前步的激活、kernel 工作区、分配器的元数据都不算有效 KV——它们各占各的显存；混进同一个数字，后面所有“为什么放不下”的诊断都会失真。

再沿逻辑步看这份状态的一生。请求到达后，prefill 一次性写入全部 prompt 的 K/V 并产出首个输出；此后每个 decode 步追加一个 token；命中 `<eos>` 或长度上限后，请求停止增长，等在途读取结束，然后释放自己的区间——`R-long`、`R-short` 是前一种结束，`R-late` 生成到长度上限即停。`R-short` 在到达的同一个逻辑步就走完了这段路；`R-long` 还要继续 decode。一个请求的终结只归还它自己的区间，其余请求的逻辑位置与所有权不变——这是第 02 章请求级合同落在容量上的直接后果。

自此 KV 从字节公式变成有所有权的请求状态。接下来两节让它进入一个真实的困境：这些区间放在哪、怎样为增长留余地。为此建立一个 24 token unit 的教学物理池（共 3072 bytes），地址按 unit 编号 0…23；三个请求带着同一份工作量先后进入。池的地址与逻辑步都是整数教学单位，不是任何真实硬件的地址，也不对应任何真实耗时。

<h2 id="max-reservation">最大预留把未知变成空占</h2>

第一版分配器的决定看起来无可指摘：输出长度在生成之前是未知的，那就按请求声明的最大上下文一次预留一段连续区间。三个请求分别声明 16、16、8——例如客户端允许的最大生成量加上 prompt；它们实际需要的只是 10、3、6。

它换到的东西是真的。地址稳定：`R-long` 在 step 0 得到区间 `[0,16)`，此后每个 decode 都在原地址追加，整个生命周期不搬一次家。边界简单：长度检查只剩一条，缓存 token 数不得超过区间容量。增长免搬迁：容量在线性区间开头就已经留好，追加永远发生在自己家里。

step 0，`R-long` 预留 `[0,16)`，写入 7 个 unit 的有效 KV（prompt 6 加首个输出）。step 1，`R-short` 到达并声明 16；池里剩余的连续空间只有 `[16,24)` 的 8 个 unit。16 > 8，申请无法满足，`R-short` 被拒绝——而它的整个生命周期本来只需要 3 个 unit。把拒绝那一刻的池账摊开：

| 池账 | token units | bytes |
| --- | ---: | ---: |
| `R-long` 有效 KV | 7 | 896 |
| `R-long` 保留未用 | 9 | 1152 |
| 空闲 | 8 | 1024 |
| 合计 | 24 | 3072 |

有效 KV 只占池子的 7/24，空闲也还有 8 个 unit，准入却失败了。失败的直接原因是“按 16 预留”这个决定，不是显存被有效状态填满。这正是必须分开的三件事：可寻址的保留容量、已经写入的有效 KV、声明了但从未用到的预留空间。表里第二、三行加起来 17 个 unit，就是 `R-short` 本可以使用的空间——它败给了自己声明的数字，不是败给当前的真实占用。

同一轨迹里 `R-late` 的经历说明这不是“预留必然失败”。step 3 `R-late` 到达时声明 8，空闲恰好是 `[16,24)` 的 8 个 unit，申请被满足，`R-late` 同样获得一段稳定地址直到 step 4 结束。方案在声明接近实际、到达彼此错开时工作良好；把它击穿的条件是声明远大于实际长度，且多个这样的请求同时在场。

还有一点不能略过：`R-long` 直到结束也只用了 16 中的 10 个 unit。即使完全没有并发，单个请求也要为“不知道会生成多长”付出 6 个 unit 的空占；并发只是把这种空占叠加到了别人的准入决策上。

<h2 id="contiguous-growth">按需增长把空间变成搬迁</h2>

另一条路把预留压到最小：到达时只申请当前长度，增长时再要新的。step 0，`R-long` 申请 7 个 unit，得到 `[0,7)`。step 1，`R-short` 到达，申请 3，拿到紧随其后的 `[7,10)`。

现在 `R-long` 要做第一次 decode，需要第 8 个 unit。原地扩展的前提是区间尾部紧邻空闲，而 `[7,10)` 已经被 `R-short` 占住。原地扩展失败，剩下的是一条必须逐步走完的链条：

1. **另址申请。** 在 `[10,24)` 里找到 8 个连续 unit，新区间是 `[10,18)`。此刻旧区间 `[0,7)` 与新区间同时存活，`R-long` 一度占用 15 个 unit，几乎是它有效 KV 的两倍——这就是搬迁期间的峰值占用。
2. **复制。** 把 7 个 token 的 K/V 从旧地址搬到新地址，并在新区间接纳第 8 个 token。
3. **地址发布。** 从这一事件起，`[10,18)` 成为 `R-long` 的权威地址，新的读取都走新地址。发布之前任何一步失败，旧地址仍是权威状态，请求可以继续在旧区间上运行——失败回滚不是恢复数据，而是根本没交出旧权威。
4. **等待在途读取。** 发布前已经开始的读取仍指向旧地址。旧区间不能立刻回收，要等这些读取逐一结束；这也是“释放”必须作为独立事件存在的原因。
5. **释放旧区间。** 在途读取归零后，`[0,7)` 被归还，池的空闲恢复。

每一步都是独立事件，而不是一次“数组扩容”式的原子操作。取消语义也从这里来：如果 `R-long` 在复制期间被取消，改变的是它自己的增长与释放流程——比如停在权威地址上做终结清理——仍然不能回收正被读取的旧区间，也不波及邻居。

同一个 step 的末尾，`R-short` 命中 `<eos>`：停止增长，在途读取结束后释放 `[7,10)`。两件事互不干扰：一个请求的搬迁不冻结别人的终结，一个请求的释放也不等待邻居搬迁。

此后的几何变得宽松。step 2、step 3，`R-long` 的尾部 `[18,24)` 是空闲的，两次 decode 都原地扩展到 `[10,19)`、`[10,20)`，地址不变，没有复制。step 3 到达的 `R-late` 在 `[0,10)` 的孔洞里得到 `[0,5)`，step 4 原地扩展到 `[0,6)`。于是在同一个池、同一份工作量下，按需方案让三个请求全部完成——这是最大预留方案没有做到的。

但“全部完成”不是免费的。代价刚刚演示过：一次完整的复制、搬迁期间 15 个 unit 的双份存活、以及一条必须逐步维护的状态机——哪个地址是权威、谁还在读旧地址、什么时候可以归还。当池更满、请求更多时，另址申请本身也会失败；那时系统面对的不再是“搬不搬”，而是“搬去哪”。

<h2 id="fragmentation-wall">空闲总量够，连续空间仍不够</h2>

看 step 1 结束时的池：`[0,10)` 空闲，`[10,18)` 属于 `R-long`，`[18,24)` 空闲。空闲合计 16 个 unit，最大的一段连续空闲只有 10。假如这一刻到达一个需要 11 个连续 unit 的请求，申请无法满足——尽管空闲总量绰绰有余。空闲被用不上的孔洞切开了。这种现象值得一个名字：**外部碎片**——空闲总量足够，但没有一段连续区间能满足申请。

现在可以把两条轨迹里出现过的所有“放不下”整理成四类。每一类的判断都回到原始区间，而不是汇总成一个占用百分比：

| 失败类别 | 判断 | 本章实例 |
| --- | --- | --- |
| 有效容量耗尽 | 即使全部空闲连续、未用预留与搬迁副本全部归还也放不下 | 本章池未出现：三请求有效合计 19 ≤ 24 |
| 过度预留 | 把保留未用的预留释放就能容纳 | `R-short` 被拒：未用 9 加空闲 8 ≥ 需求 16 |
| 搬迁峰值 | 等搬迁的旧区间归还就能容纳 | `R-long` 双份存活期间的申请 |
| 外部碎片 | 空闲总量够，最大连续不够 | step 1 末的 11-unit 申请 |

四类失败对应四种候选动作，而每种动作改变的都是一份合同，不是免费的除弊：压缩要把占用区间搬到一起，用更多复制与在途等待换取连续；退回大块预留，用空占换取稳定地址；拒绝增长把容量问题变成请求失败；排队等待把失败变成延迟，并且要求有人回答等谁、让谁。本章不在这中间选边——先看清楚每个动作改的是哪一条合同。

于是留下一个形式化的问题。token 的逻辑顺序必须连续：位置 0…n 的语义、因果可见范围、按位置的读取都建立在它上面；但物理存储是否必须是单一连续区间？两条连续方案共同维护的合同可以列出来：逻辑位置到存储位置的映射、每步在末尾追加一个位置、在途读取依赖权威地址、请求独立地终结与回收。任何替代布局必须原样保住这四条。至于它怎样保住——那是下一章的事。

最后重申证据边界。本章的池、地址、unit 与逻辑步都是整数教学单位：它们能证明的是在这些明确规则下，哪些申请会失败、失败应归因于哪一类容量问题；不能证明真实 GPU 的显存粒度、复制带宽或 OOM 行为，那些判断必须在指定软硬件上测量。碎片与预留浪费本身也不是教学虚构——已发表的服务系统分析记录过同样的现象——但本章的每个数字只对本章的规则负责。
