第 01 章最后得到的执行器一次只照顾一个请求。它知道怎样从 prefill 进入 decode，怎样在发送前检查输出许可，也知道终止时要等在途工作安全结束再释放 KV。现在不修改这个执行器内部的任何一条规则，只让三个请求先后走进同一个服务。问题看似只是“多开几个循环”，但在动手以前，我们需要看清究竟多出了什么。

<h2 id="multiple-requests">当第二个请求到达</h2>

先固定三份请求，后面不再为了让某种方案显得更好而更换它们。`R-long` 在逻辑步 0 到达，prompt 有 6 个 token，需要产生 4 个输出；`R-short` 在步 1 到达，prompt 只有 2 个 token，首个输出就是 `<eos>`；`R-late` 到步 3 才出现，prompt 有 4 个 token，生成 2 个 token 后触及长度上限。

| 请求 | 到达 | prompt token | 输出 token | 结束原因 |
| --- | ---: | ---: | ---: | --- |
| `R-long` | step 0 | 6 | 4 | `eos` |
| `R-short` | step 1 | 2 | 1 | `eos` |
| `R-late` | step 3 | 4 | 2 | `length` |

这里的 **逻辑步** 只是把事件先后摊开的离散刻度。一个 prefill 和一个 decode 在图上都占一步，不表示它们真实耗时相等，更不对应一毫秒。这个小模型能证明“谁在谁之前”“哪个位置没有有效工作”，不能证明任何 GPU 的延迟、吞吐或利用率。

三个请求虽然共享服务，却仍有三份独立合同。`R-short` 选到 `<eos>` 时，只能终止自己的生成；`R-long` 的 KV 仍要保留给下一次 decode；`R-late` 尚未到达，更不能被前一请求的结束动作波及。每个请求继续独立持有生成状态、KV 使用权、输出许可、终止原因和最终清理责任。并发改变的是工作怎样被选择，不是把三个生命周期熔成一个。

最谨慎的服务实现几乎不用改第 01 章代码：请求到达后进入 FIFO 队列，执行器取出队首，把它从 prefill 一直运行到结束，再取下一个。它没有共享 KV 的歧义，也没有两个循环同时修改设备状态；取消和清理仍发生在原来的单请求边界。作为第一版服务，这个设计非常合理。

把固定请求放进去，原始轨迹却暴露出一个新现象：

| 逻辑步 | 新到达 | 被设备执行的有效工作 | 仍在等待 |
| --- | --- | --- | --- |
| 0 | `R-long` | `R-long` prefill，产生 `y1` | — |
| 1 | `R-short` | `R-long` decode，产生 `y2` | `R-short` |
| 2 | — | `R-long` decode，产生 `y3` | `R-short` |
| 3 | `R-late` | `R-long` decode，产生 `y4` 并结束 | `R-short`、`R-late` |
| 4 | — | `R-short` prefill，产生 `<eos>` 并结束 | `R-late` |
| 5—6 | — | `R-late` prefill、decode 后结束 | — |

`R-short` 自己只需要一次模型执行，却从 step 1 等到 step 4 才第一次被选中。这三步不是它的 tokenizer 更慢，也不是它的模型计算更多；唯一原因是队首的 `R-long` 尚未结束，而当前策略不允许切换请求。到这里，**队头阻塞**才有了具体含义：排在前面的长工作决定了后续短工作的等待，即使短工作已经满足执行前提。

注意“已经到达”和“可以被执行”仍不是同一句话。请求可能在等待 tokenizer、输入校验或前序依赖，那叫尚未可运行；也可能像 step 1 的 `R-short`，prompt 已经准备好，却因为选择策略没有得到执行机会。事件记录必须分别保留 `arrived`、`became-ready`、`host-submit`、`device-start` 和 `device-complete`，否则看到一个长等待时，我们无法判断缺口在请求准备、服务选择还是设备执行。

串行队列没有变得不正确。它用简单的所有权和顺序换来了可预测性，只是这个交换在交互式服务里可能让短请求等待太久。现在自然会问：既然 `R-short` 已经可运行，为什么不让它也拥有自己的执行循环？

<h2 id="independent-loops">两个循环不等于两份设备时间</h2>

为每个请求创建一个线程或协程，是从串行队列迈出的最小一步。`R-long` 等待设备完成时，事件循环可以接收 `R-short`、完成输入处理并让它提交 prefill；网络发送、停止判断和取消监听也不必被另一个请求的 Python 调用完全挡住。此时多个请求的控制流可以交错推进，这就是这里首先得到的 **并发**：在同一时间区间内，系统有多项尚未完成的任务，它们轮流取得推进机会。

但主机上的两个循环都在运行，只说明它们都能发出设备工作，并没有说明设备怎样执行这些工作。考虑这段只记录边界、不填写耗时的事件：

```text
H0  R-long  host-submit(decode)
H1  R-short host-submit(prefill)
D0  R-long  device-start
D1  R-long  device-complete
D2  R-short device-start
D3  R-short device-complete
```

两个 `host-submit` 可以相距很近，设备事件仍可能按顺序出现。若运行时把工作放进同一条有序队列，后一项要等前一项；若使用不同 stream 且硬件有剩余资源，两项也许能够部分重叠；依赖、隐式同步、kernel 规模和设备资源又可能让这种重叠消失。异步接口表达了“允许先返回和继续提交”，没有承诺“提交的工作必然同时执行”。

因此需要把三个问题分开。主机控制流能否交错，观察线程、协程和提交事件；设备工作是否重叠，观察 stream、device start/complete 与 profiler 轨迹；多个请求是否进入同一次模型执行，则观察执行输入中是否同时出现多个 request id。把它们都叫“并行”会掩盖完全不同的工程合同。

每请求一循环仍有价值：它让接收、预处理、发送和取消不必全局串行，也让请求在设备队列中有机会交错。但如果每个循环都提交 batch size 为 1 的模型执行，它没有主动把两个请求的张量组合起来。设备可能看到一串更密集的小工作，也可能看到同步和调度开销；究竟更快还是更慢，需要固定模型、形状、stream 和硬件后测量，不能从协程数量推出。

更麻烦的是，独立循环各自只知道自己的下一步。`R-long` 准备做一个单 token decode，`R-short` 准备做一次两 token 的 prefill；它们若同时争用同一个模型执行入口，需要有人裁决提交顺序、在途限制和错误传播。把一个互斥锁放在入口前可以恢复安全，却可能只是把 FIFO 从“请求级”缩小成“模型调用级”。我们减少了整请求阻塞，仍没有回答哪些工作应该合在一起。

于是问题从“怎样让多个控制流活跃”变成“能否让一次设备执行同时推进多个请求”。这才把我们带到 batch，而不是线程数量本身。

<h2 id="static-batch">把等待的请求放进同一次执行</h2>

在 step 0 立即执行 `R-long` 并不是唯一选择。服务也可以短暂等待，到 step 1 看见 `R-short` 后，把两份 prompt 放进同一次 prefill。模型权重只需面对一个包含两个样本的输入，设备获得更大的并行工作形状。这个动机并不荒唐：若单个请求提供的工作太小，合并独立样本常常能给硬件更多同时可做的运算。

两份 prompt 的长度却不同。若教学实现使用规则的二维张量，并把本批都对齐到最长 prompt 6，输入槽位可以写成：

```text
R-long   x1 x2 x3 x4 x5 x6     6 个有效位置
R-short  s1 s2  ·  ·  ·  ·     2 个有效位置 + 4 个 padding 位置
```

**padding** 是为了把不同长度的序列表示成规则形状而补出的占位。它不属于 `R-short` 的 prompt，不能进入生成工作量或正确性结论。在这个朴素矩形模型里，批次有 12 个位置，其中 8 个有效、4 个只负责对齐。Attention mask 可以阻止占位改变语义，但“语义上被屏蔽”不自动证明某个具体 kernel 完全没有处理成本；实际实现可能计算、跳过、压紧或采用另一种布局，必须看实现与测量。

这里也出现了第一项策略等待：`R-long` 在 step 0 已经可运行，却为了凑到第二个成员而等到 step 1。若随后真的获得更好的设备效率，这个交换可能值得；若到达稀疏或等待上限太长，它可能只是平白增加首个输出的等待。batch size 不是越大越好，因为形成 batch 本身就需要回答“等谁、等多久、何时不再等”。本章不替真实服务填写这个答案。

静态 batch 至少解决了一个明确问题：一次 prefill 的输入中确实同时有 `R-long` 和 `R-short`，不再只是两个主机循环分别提交。可是它悄悄引入了一个新假设——这两个请求在接下来的一段时间里要作为固定成员一起推进。prompt 只执行一次时，长度对齐已经付出代价；进入自回归 decode 后，成员的生命周期差异会更明显。

<h2 id="batch-diverges">同一批请求不会一起结束</h2>

这次联合 prefill 同时给两个请求产生首个 token。对 `R-short`，首个 token 就是 `<eos>`，它应当登记自己的结束原因、关闭自己的输出并在安全点释放自己的 KV。`R-long` 只产生了 `y1`，还要再做三次 decode。请求级合同不允许为了维持 batch 外形而假装 `R-short` 仍在生成。

若静态 batch 固定两个成员直到最长请求结束，后续占用会变成：

| 执行步 | `R-long` 槽位 | `R-short` 槽位 | 批次之外 |
| --- | --- | --- | --- |
| prefill | 6 个有效 prompt 位置 | 2 个有效位置 + 4 个 padding | — |
| decode 1 | 1 个有效 token | 已结束，非活跃槽位 | — |
| decode 2 | 1 个有效 token | 已结束，非活跃槽位 | `R-late` 在此时到达并等待 |
| decode 3 | 1 个有效 token，随后结束 | 已结束，非活跃槽位 | `R-late` 继续等待 |

表中的 **非活跃槽位** 与 prefill padding 不是同一种浪费。padding 来自一次执行中输入长度需要对齐；非活跃槽位来自 batch 成员已经结束，策略却仍保留固定位置。前者可能让设备处理不属于有效 prompt 的位置，后者可能表现为空掩码、占位输入，或者干脆没有为该位置提交有效工作。若只汇总成一个“利用率”，就失去了修正设计所需的原因。

请求与 batch 槽位也不能混为一物。`R-short` 的槽位可以在元数据中保留为 inactive，但它的终止原因、输出流和 KV 租约应按自己的安全边界收束。反过来，若实现为了简化 batch 管理而一直占着已经结束请求的 KV，那是需要记录的容量代价，不是静态 batch 的语义要求。

为什么不立刻删除 `R-short`，把 `R-late` 填进空位？因为 `R-late` 在当前 batch 建立之后才到达。允许它加入意味着下一次执行前要重建成员列表、输入位置、KV 引用和输出映射；若上一批工作仍在途，还要先确定哪些元数据可以安全修改。这可能是更好的方向，却已经不再是“成员固定直到整批结束”的静态 batch。

保持固定成员的 batch 可以称为 **封闭批次**：形成之后，新请求只能等待下一批。它比逐请求串行更充分地合并了同时到达的工作，也比独立循环更明确地构造了批量输入；与此同时，它把完成时间不同的请求绑在共同边界上，并把晚到请求挡在批外。旧模型再次不是完全错误，而是无法同时满足形状效率、短请求及时完成和动态到达。

比较三种轨迹时，必须保留第 00 章的证据边界。请求集合、到达步、prompt 长度、输出 token 数和终止原因都相同，才可以把逻辑等待差异归因于策略。有效 token、padding、非活跃槽位、批外等待和失败要分别记录。即使某种策略在教学轨迹中更早完成 `R-short`，也只证明当前离散规则改变了事件顺序；真实 kernel 效率、GPU 重叠和端到端收益仍要在同条件环境中测量。

<h2 id="next-choice">下一次执行该选谁</h2>

串行队列一次选择一个请求，并把选择维持到请求结束；独立循环让多个请求各自提交，却把设备顺序交给入口和运行时；静态 batch 一次选择一组成员，并把组保持到最慢成员结束。三种方案的共同缺口现在可以写成同一个问题：当一项设备工作完成后，系统应该根据当前状态选择哪些请求组成下一次执行？

这个问题在每个执行边界都会重来，因为集合不断变化。新请求到达，旧请求从 prefill 进入 decode，有的请求等待上一项设备工作，有的已经命中停止条件，还有的可能被取消。一次选择至少要知道：请求是否到达且完成输入准备，当前 phase 和下一份有效输入是什么，是否有工作仍在途，终止权是否已经登记，以及下一步依赖的 KV 使用权是否有效。缺少其中任一项，都可能选择一个尚不可运行、已经结束或资源并不安全的请求。

选择还必须输出可复核的执行合同：这一组包含哪些 request id，每个成员贡献多少有效 token，哪些位置只是对齐或非活跃状态，执行完成后怎样把 logits、KV 更新和错误重新归还给各自请求。batch 是一次模型执行的形状，不是新的业务身份；请求才拥有输出和终止语义。

我们尚未给这个选择过程命名，也没有证明某种策略是最佳答案。要让成员在每一步加入或退出，系统首先得回答一个更低层的问题：每个请求不断增长的 KV 到底占多少空间、放在哪里、能否扩容，以及结束后怎样独立回收。若容量模型仍是假设“每个请求预留一整块连续最大空间”，再灵活的选择也可能很快被显存分配击穿。

因此下一章先离开调度策略，追踪 Attention 在每个 token 后留下的 KV 状态。等它的大小、增长和所有权约束清楚之后，我们才有资格回到“下一次选谁”，让执行成员真正动态变化。第 02 章需要留下的不是一个现成调度器，而是一组无法再被绕开的输入：原始到达、可运行状态、执行 phase、形状、在途边界和请求级资源合同。

如果现在看到一份报告说“我们给每个请求开了协程，所以 GPU 已经并行，队头阻塞也解决了”，你应当先要求三类证据：主机提交是否真的交错，设备 start/complete 是否重叠，以及一次模型执行是否包含多个请求。它们回答不同问题；缺少后两类事件，协程数量仍不能证明真实 GPU 性能。
