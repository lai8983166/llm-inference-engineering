一份优化报告摆在你面前：实现 A 用时 `100 ms`，实现 B 用时 `70 ms`。报告的结论只有一句——**B 快了 30%**。数字很整齐，差距也远大于计时器的小数误差，看起来已经足够决定是否合并这项优化。

先不要急着讨论 30% 应该叫耗时下降还是速度提升。更早的问题是：这两个数字是不是在描述同一件事？报告没有原始记录，只写了 A 生成 32 个 token，B“提前遇到停止条件”生成 20 个。若每生成一个 token 都需要继续工作，那么 B 少做了十二步。它可能有更好的实现，也可能只是更早结束；`100` 和 `70` 把实现差异、工作量差异以及输出差异压成了同一列。

这就是本章的起点。benchmark 不是先挑一个计时 API，再把函数包起来。它首先是一项待审查的主张：比较对象是否等价，观察边界是否一致，结束事件是否真的表示工作完成，运行是否处在要回答的阶段，以及汇总数字是否保留了原始样本中的重要差异。我们会逐次修补这份报告。每次修补之后都不宣布“现在科学了”，而是继续问：**当前证据仍然不能排除什么解释？**

<h2 id="same-work">快了 30%，但做的是同一件事吗？</h2>

最自然的修正是把输出长度固定成 32。可对于生成系统，“输出 32 个 token”也还没有完整描述任务。A 使用贪心选择，B 使用随机采样；A 的 temperature 为 0，B 的 temperature 为 0.8；两边即使拿到相同输入，也可能沿不同 token 继续生成。不同 token 不只改变文本，还可能改变停止时刻和后续每一步的输入。一个控制生成行为的配置变化，同时改变了输出质量、工作量与耗时。

于是我们需要先写下一个**正确性合同**。合同不是要求所有输出逐字相等，而是声明本次比较认为什么叫“完成同一任务”。对于确定性的算子替换，可以要求相同输入下数值落在约定误差内；对于固定解码路径的回归，可以固定生成配置和随机源，再比较 token 序列；对于本就允许多种答案的随机生成，则应规定独立的质量接受条件、输出长度范围和失败条件。质量若发生变化，必须单独报告，不能让更短或更差的答案以“优化”身份进入耗时列。

这也解释了为什么“固定 seed”不是万能修复。seed 只控制已知随机源的一部分；软件版本、设备、数值顺序和某些非确定性实现仍可能让结果不同。反过来，逐位相同也未必是合理的产品合同。关键不是选择最严格的相等方式，而是让第三方知道：两边接受了什么输入，使用了哪些会改变生成的配置，做了多少可见工作，怎样判定输出仍然满足任务。

对 A/B 报告的第一轮修正可以写成：同一组输入，各 128 个输入 token；最多生成 32 个 token；相同模型版本与生成配置；两边都成功产生 32 个 token；输出通过同一接受条件。原来的 `100 ms` 对 `70 ms` 已经作废，因为它们不满足这个合同。重新运行得到 A 为 `100 ms`、B 为 `92 ms`。差距缩小了，但至少“B 少做了工作”不再是眼前的解释。

现在能说 B 更快了吗？仍然不能。报告只写了“耗时”，没有写这段时间是由谁看见的。

<h2 id="observer-window">秒表从谁的世界开始？</h2>

一次调用穿过多个边界。客户端开始等待，网络稍后把请求送到服务端；服务端可能先验证和排队，再由主机代码向设备提交工作；设备完成后，结果还要回到主机、被编码并传回客户端。它们都在同一次请求里，却不共享同一个问题。

假设一条记录保留了以下事件。这里的数值是 `simulated` 教学数据，只用于手算事件差值：

| 观察者 | 起始事件 | 时间 | 结束事件 | 时间 | 可重建的区间 |
| --- | --- | ---: | --- | ---: | ---: |
| 客户端 | 开始请求 | 0 ms | 收到完整结果 | 80 ms | 80 ms |
| 服务端 | 接收请求 | 8 ms | 完成响应 | 74 ms | 66 ms |
| 主机提交代码 | 提交设备工作 | 18 ms | 提交函数返回 | 20 ms | 2 ms |
| 设备事件 | 设备开始执行 | 21 ms | 设备完成执行 | 68 ms | 47 ms |

四个数字都可以由各自的起止事件正确相减，却回答四个不同问题。客户端的 80 ms 包含网络和服务端经历；服务端的 66 ms 不含请求到达前与响应返回后的时间；设备的 47 ms 只覆盖被两个设备事件夹住的工作。主机的 2 ms 更特殊，我们很快会处理它。若 A 的 `100 ms` 来自客户端，而 B 的 `92 ms` 来自服务端，那么两列即使单位相同也没有可比性。

因此一个延迟指标至少需要三个部分：**观察者、起始事件、结束事件**。指标名称是这三个选择的简称，不是替代它们的魔法词。所谓端到端延迟，若没有说明“谁的端到端”，仍可能把客户端与网关、网关与服务进程、服务进程与设备混在一起。计时器也必须属于明确的时钟域；客户端时钟的绝对读数不能直接减去服务端时钟的绝对读数，除非另有经过验证的校时与误差模型。

<ObservationBoundaryFigure />

工程记录不应只保存最终的 `duration_ms`。至少保留运行标识、观察者、事件名和单调时间，再由声明过的窗口计算差值。这样当问题从“用户等了多久”变成“服务端处理了多久”时，可以重新选择同一观察者下的合法事件，而不必猜测旧数字包含了什么。若起点或终点缺失、来自不同观察者，或者结束时间早于开始时间，正确结果不是 `0 ms`，而是拒绝计算并说明证据缺口。

第二轮报告于是固定为：A 与 B 都使用客户端的“开始请求→收到完整结果”。A 是 `100 ms`，B 是 `92 ms`。这次观察窗口相同，但报告的实现者提出一个反对意见：他们真正优化的是设备执行，网络波动不应掩盖改动。这个诉求合理，只是需要另设设备窗口并同时报告，不能把两种窗口偷换成一列。

当他们为 B 添加设备计时时，却得到一个令人振奋得过头的结果：`2 ms`。问题不再是时钟精度，而是那个结束事件是否真的意味着工作结束。

<h2 id="async-completion">函数返回，工作真的结束了吗？</h2>

主机负责组织程序，设备负责执行被提交的计算。为了让二者可以重叠，许多设备接口不会等工作做完才把控制权还给主机。提交函数返回，只能证明主机已经完成了这次提交；设备工作可能尚未开始，也可能正在执行。若秒表紧贴在提交调用两侧，它量到的是提交路径，而不是被提交工作的执行时间。

```text
t0 = host_clock()
submit_work_to_device()
t1 = host_clock()
report(t1 - t0)       # 这里只观察到“提交返回”
```

这正是上一节 2 ms 的来源。事件线已经告诉我们设备从 `21 ms` 工作到 `68 ms`，主机却在 `20 ms` 就停止计时。一个结束于 20 ms 的窗口不可能覆盖 21 ms 才开始的工作。计时器没有撒谎，它忠实回答了错误的问题。

<AsyncCompletionFigure />

修复方式取决于想回答什么。若要测客户端等待，继续使用客户端完成事件；若要测设备区间，应在目标执行流上记录设备开始与设备完成事件，并在读取结果前确认完成事件已经发生；若必须用主机时钟覆盖异步工作，就需要等待与本次工作对应的安全完成点，然后再读结束时间。笼统地在每轮调用全设备同步也能阻止提前结束，但它可能消除原本存在的重叠、扩大计时窗口或给每轮增加额外成本。同步不是免费的“让数字变准”按钮，它是实验设计的一部分，必须记录同步的对象和位置。

同理，设备 event 也不是放在哪里都正确。event 只度量它所在执行序列中两个记录点之间的区间；它可能不含主机调度、数据准备、排队、结果处理或其他 stream 上未建立依赖的工作。一个完成 event 证明的是它所代表的先行工作已经到达该点，不自动证明客户端已经看到结果，更不证明整次请求已经释放资源。

第三轮报告保留两类结果：客户端 A=`100 ms`、B=`92 ms`；设备窗口 A=`52 ms`、B=`47 ms`。现在可以说，在这次模拟记录、同一任务合同和各自一致的窗口下，B 的观测耗时较低。还不能说改动导致了稳定收益，因为每个实现目前都只有一次运行，而且两边第一次运行的历史并不相同。

<h2 id="cold-and-steady">第一次为什么总不一样？</h2>

团队继续各跑六次，得到下面的客户端耗时。所有样本仍是 `simulated`，没有删除任何一轮：

| 运行序号 | 1 | 2 | 3 | 4 | 5 | 6 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| A / ms | 168 | 112 | 103 | 100 | 101 | 99 |
| B / ms | 240 | 125 | 92 | 90 | 91 | 89 |

若只看第一次，B 明显更慢；若只看最后三次，B 明显更快。两种读法都来自真实保留的样本，区别在于它们回答的部署问题不同。进程首次处理请求时，可能发生模型加载、内存分配、代码生成、算法选择或缓存填充。后续运行可以复用其中一部分状态。把前几次运行称为 warm-up，并不能自动证明它们应该被删除；它只是承认系统状态正在改变。

如果问题是“新实例收到首个请求时用户等多久”，第一次运行正是目标，排除它会删掉最重要的成本。如果问题是“常驻实例进入稳定阶段后的单次执行表现”，则可以在正式采样前执行声明数量的预热，但必须说明预热做了什么、为什么认为目标状态已经建立，并保留原始轨迹供复核。不能先看曲线，再把不喜欢的点统称为 warm-up。冷启动和稳态应作为两个不同结论报告。

<WarmupSequenceFigure />

运行历史以外，工作负载和环境也在塑造数字。输入 token 数影响需要处理的上下文，实际输出 token 数改变生成步数，请求形状可能触发不同代码路径；模型 revision、精度、量化与生成配置决定做什么计算；GPU 型号、功耗或频率状态、驱动、运行时、框架 commit 和编译选项决定怎样执行。并发数和到达模式也应固定并记录，但它们如何形成排队与服务指标要等后续章节再系统推导，本章只要求别让它们在 A/B 之间悄悄变化。

最小环境记录不是为了把机器清单写得很长，而是为了判断一次差异能否归因。若 A 与 B 唯一有意改变的是实现，其余已知条件相同，差异才有机会隔离这项改动；若硬件或软件栈同时变化，报告应缩小结论范围或补做对照。即便条件完全相同，测得相关差异也只是支持候选因果解释，不能排除所有未记录因素。

到这里，我们已经知道该怎样形成稳态样本，却还没有回答该从多次运行中拿走哪个数字。只报最好的一次会选择性隐藏噪声；只报平均值，也可能把少数严重慢样本磨平。

<h2 id="evidence">一个数字如何变成证据？</h2>

看另一组同条件稳态结果。A 的十次耗时是 `96, 98, 99, 100, 100, 101, 102, 103, 104, 106 ms`；B 是 `80, 82, 84, 86, 88, 90, 92, 94, 120, 130 ms`。B 的平均值约为 `94.6 ms`，低于 A 的 `100.9 ms`；B 的中位数为 `89 ms`，也更低。但按 nearest-rank 方法取第 90 percentile，B 是 `120 ms`，A 是 `104 ms`。B 的中心更好，慢端却更差。

<DistributionFigure />

这不是要求所有报告固定使用 mean、median 和 p90。它说明聚合方法是一种信息选择：mean 会受所有样本影响，median 描述排序后的中间位置，尾部 percentile 观察较慢区域。该选择应该来自使用场景和要保护的风险，而不是来自哪个数字最好看。样本很少时，尾部估计本身也不稳定，所以必须同时报告样本数、失败数和原始观察，避免把一个带两位小数的 percentile 误装成确定事实。

现在可以把一路修补的内容收束成最小 benchmark 协议。它不是突然出现的最佳实践模板；每一项都对应我们已经遇到的一种错误解释：

| 协议内容 | 它阻止什么错误解释 |
| --- | --- |
| 任务、输入集、生成配置、随机性与输出接受条件 | 把少做工作或降低质量当成优化 |
| 模型/实现版本、硬件和关键软件环境 | 把同时变化的环境归因给代码改动 |
| 输入、输出、请求形状与并发等工作负载 | 比较实际上不同的执行量或代码路径 |
| 观察者、起始事件、结束事件与时钟/同步方式 | 用同名数字比较不同窗口，或在异步工作完成前停表 |
| 冷启动或稳态问题、warm-up 与排除规则 | 事后选择有利样本，混同不同运行阶段 |
| 原始事件、成功/失败、样本数与聚合方法 | 只留下最佳值或让平均值掩盖慢端和失败 |
| 结论范围与证据来源 | 把相关性写成因果，把模拟轨迹写成真实 GPU 收益 |

把这些字段连起来，第三方应能从原始事件重新算出报告的窗口，识别不满足合同的运行，重现聚合结果，并判断结论有没有越界。若只剩一张“B 快 30%”的截图，即使数字来自一次真实 GPU 运行，也还不是完整证据；若记录来自本章的模拟轨迹，它最多证明事件合同与计算过程一致，绝不能证明某个 GPU、模型或框架的性能。

因此，这份报告最后能写的不是“B 普遍更快”，而是：“在声明的模型版本、单请求工作负载和稳态策略下，十次模拟记录中 B 的中位客户端耗时低于 A，但 B 的慢端样本更高；该轨迹只验证测量协议，真实设备收益仍需按同一协议实测。”这句话不如 30% 醒目，却清楚区分了观察、比较和尚未证明的因果。

我们还留下了一个刻意未拆开的词：**完成**。本章只把它当作计时窗口需要选择的事件。但一次生成请求内部，模型执行、token 选择、文本可见、停止决定与资源释放并不发生在同一刻。要真正知道客户端完成、设备完成和请求结束各自意味着什么，下一章将进入一次请求内部，追踪它怎样一步步活着。
