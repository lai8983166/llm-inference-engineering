# LLM Inference Engineering

一套面向推理系统开发者的、问题驱动的工程训练项目。

这个项目不把 vLLM、SGLang 的现有机制当作需要照抄的答案。课程从朴素但合理的实现开始，通过资源约束、反例、故障注入和真实性能证据，让学习者亲自发现旧设计为什么失效，再从失败中推导新机制必须满足的不变量。真实框架只在推理链形成之后出现，用来比较生产实现如何处理相同约束。

## 项目定位

`llm-inference-learn` 是快速入口：它建立从请求生命周期、GPU、KV、调度到压测和框架选型的系统地图。

本项目是后续工程主线：学习者将逐步实现一个可运行、可测试、可观测、可压测的推理服务，并最终进入 vLLM、SGLang 的真实源码，完成可以解释和验证的修改。

教学不能直接赋予生产经验，但可以提供接近真实工作的训练条件：不完整需求、资源上限、长短请求混合、取消与超时、并发交错、测量噪声、错误归因、性能回归和代码审查。学习成果以代码和证据判断，不以阅读进度判断。

## 毕业开发者画像

完成主线后，学习者应当能够：

- 从自回归模型语义推导一次请求在服务端的状态和资源生命周期。
- 建立权重、激活、工作区和 KV cache 的显存账本，并说明估算误差来自哪里。
- 从连续分配的失败中推导分页 KV，设计 block table、所有权、引用和回收不变量。
- 实现连续批处理、准入、抢占与公平性策略，并分析它们对 TTFT、ITL、吞吐和 goodput 的影响。
- 正确处理流式输出、取消、超时、失败和资源释放，而不只让正常路径运行。
- 设计可复现的开放环与闭环压测，保留从原始事件到聚合结论的证据链。
- 使用 profiler 和最小对照实验定位 CPU、kernel、带宽、同步或调度瓶颈。
- 阅读 vLLM、SGLang 的关键调用链，把课程中的不变量映射到真实数据结构和并发边界。
- 对真实框架提交一个带测试、benchmark、风险说明和回退条件的小型修改。
- 面对新约束时重新推导方案，而不是把某个框架机制当作无条件最佳实践。

## Lab 如何组织知识

每个核心机制至少经历一个完整的问题链。Lab 不会以“实现 PagedAttention”“实现 continuous batching”开场，而以尚未给出答案的工程任务开场。

1. **建立朴素版本**：实现当前认知下最直接、能够正确工作的方案。
2. **运行前预测**：记录对容量、延迟、吞吐和故障行为的判断，禁止事后改写。
3. **加入反例**：通过未知输出长度、长短请求混合、并发结束、取消或资源不足暴露矛盾。
4. **收集原始证据**：检查事件、状态、分配轨迹和 profiler 数据，不先接受聚合结论。
5. **定位第一处错误假设**：区分正确性、容量、性能和公平性问题。
6. **推导约束与不变量**：先写系统必须保证什么，再讨论机制名称。
7. **比较候选设计**：记录被排除方案、成立条件和新增复杂度。
8. **实现并验证**：加入单元测试、不变量测试、故障注入和同条件 benchmark。
9. **再次破坏新方案**：改变 block size、负载、并发顺序或失败条件，寻找失效边界。
10. **映射真实框架**：阅读 vLLM、SGLang 对同一问题的处理，并解释差异来自哪些约束。

因此每个主题通常由三类 Lab 组成：探索 Lab 负责发现“为什么需要”，构造 Lab 负责回答“怎样实现”，失效 Lab 负责回答“什么时候不成立”。

## 主线章节

主线围绕同一个推理服务持续演进。后续章节必须保留并面对前面已经产生的状态、接口和技术债，避免每章都从一份无历史负担的示例代码重新开始。

| 章节 | 核心问题与故意暴露的失败 | 主要工程产物 |
| --- | --- | --- |
| 00. 建立可相信的基线 | 什么叫“正确”和“更快”？先固定模型输出、随机性、计时边界、硬件与软件环境，识别 warm-up、异步执行和测量窗口造成的假象。 | 环境清单、确定性基线、事件记录器、首份 benchmark 协议 |
| 01. 一次请求怎样活着 | 从 tokenizer、prefill、采样、decode 到 streaming 建立最小请求状态机；用停止条件、客户端断开和异常输入破坏“一个 API 调用就是一次 forward”的模型。 | 单请求执行器、状态轨迹、资源生命周期图、取消测试 |
| 02. 朴素并发为什么不够 | 先用“一请求一执行循环”和静态 batch 服务并发，再用长短请求混合暴露 padding、队头阻塞、GPU 空洞和不可控排队。 | 朴素服务、请求队列、并发工作负载、失败分析报告 |
| 03. KV 为什么成为系统状态 | 从 Attention 张量推导每 token KV 字节数和布局；让未知输出长度、扩容和不同结束顺序击穿最大预留与连续增长方案。 | KV 显存账本、连续分配器、分配轨迹、碎片反例 |
| 04. 从碎片推导分页 KV | 不预告分页答案，先从离散增长、物理位置解耦和独立回收等约束比较候选分配策略，再实现 block pool、block table 和回收。 | 分页分配器、引用/所有权不变量、block-size 对照实验 |
| 05. 从静态 batch 推导连续调度 | 让请求在不同时间到达和完成，推导调度 tick、可运行集合与动态 batch；观察 prefill、decode 竞争如何同时改变 TTFT 和 ITL。 | continuous batching scheduler、时间线、策略对照报告 |
| 06. 容量不足时谁应该等待 | 加入 KV 水位、突发流量和不同优先级，比较无界排队、准入拒绝、抢占和重计算；处理吞吐、尾延迟、公平性与浪费之间的冲突。 | 准入控制器、抢占协议、公平性测试、过载复盘 |
| 07. 正常路径之外的服务语义 | 将取消、超时、客户端慢消费、worker 异常和部分输出纳入状态机，验证任意终止路径都能释放 KV、队列位置和流对象。 | 流式服务接口、故障注入器、资源泄漏测试、事件语义文档 |
| 08. 指标如何成为可复核证据 | 从原始事件定义 queue time、TTFT、ITL/TPOT、E2E、吞吐和 goodput；比较开放环与闭环，制造“均值更好但 SLO 更差”的反例。 | 可复现压测器、原始事件集、聚合报告、错误结论案例库 |
| 09. 优化为什么可能没有收益 | 从 profiler 证据区分 Python/CPU 调度、launch、同步、显存带宽和计算瓶颈；用错误优化和测量噪声训练因果归因。 | 性能剖析报告、最小对照实验、优化前后证据链 |
| 10. 机制组合为何产生新问题 | 引入 prefix cache、结构化输出或投机解码中的至少一项，让共享所有权、缓存失效、调度预算和收益分布重新进入设计。 | 机制扩展、命中/失败观测、组合回归测试、适用边界 |
| 11. 从教学引擎进入真实框架 | 沿一次请求追踪 vLLM、SGLang 的入口、scheduler、KV 管理、worker 和指标路径；不按文件逐页阅读，而按课程不变量查找生产实现。 | 双框架调用链地图、关键数据结构笔记、版本化源码锚点 |
| 12. 真实修改与结课事件 | 从性能回归、资源泄漏、调度异常或小型功能需求中选择一个问题，在真实框架中完成诊断、设计、实现、测试、benchmark 和复盘。 | 可审查 patch、设计说明、测试、benchmark 原始数据、结课答辩 |

## 深化分支

章节 00—09 是共同主线。完成共同主线后，学习者至少选择一个深化分支，并在第 11、12 章把分支能力应用到真实框架。分支不是彼此隔离的职业标签，而是对同一推理系统采用不同的观察尺度。

### A. Kernel 与硬件性能

面向希望深入 GPU 数据路径的开发者。内容从算子边界和 memory hierarchy 开始，逐步进入 kernel fusion、paged attention 数据访问、CUDA Graph、量化 kernel 和多 stream 同步。训练重点不是复刻一个最快 kernel，而是根据 profiler 证据解释瓶颈、建立正确性基线，并证明优化没有改变数值和服务语义。

毕业分支产物：一个真实 kernel 或执行路径优化、数值回归测试、跨形状 benchmark 和失效范围说明。

### B. KV、调度与吞吐系统

面向希望深入推理引擎控制面的开发者。内容继续扩展分层 KV、prefix sharing、缓存淘汰、chunked prefill、优先级、抢占、预测长度误差和 speculative decoding 的调度影响。训练重点是跨 allocator、scheduler 和 worker 维护不变量，而不是单独调一个启发式参数。

毕业分支产物：一个资源或调度策略修改、对抗负载、活性/安全性测试和 SLO 对照报告。

### C. Serving、可靠性与多租户

面向希望把推理引擎运行成长期服务的开发者。内容覆盖 API 语义、背压、超时传播、隔离、限流、过载保护、滚动升级、可观测性和容量规划。训练重点是处理部分失败与负载漂移，并从线上症状回溯到请求、调度和 GPU 证据。

毕业分支产物：一次故障演练、事件级追踪、恢复方案、容量模型和事后复盘。

### D. vLLM / SGLang 贡献者

面向希望直接参与框架开发的学习者。内容包括版本化源码阅读、最小复现、测试组织、benchmark 规范、向后兼容、配置边界和代码审查。学习者必须分别追踪两个框架对同一问题的实现，避免只熟悉一个仓库的命名。

毕业分支产物：至少一个真实框架的可审查修改，以及另一框架的对应机制比较。是否合并不作为毕业条件，修改的推理、正确性和证据质量才是评价对象。

## 实践环境分支

为了避免硬件条件阻断早期学习，项目提供两条环境路径，但不会把模拟结果冒充真实性能结论。

- **可移植路径**：在 CPU 或普通开发机上运行状态机、allocator、scheduler、故障注入和确定性事件回放，完成正确性与系统推理训练。
- **真实 GPU 路径**：从第 00 章开始记录真实设备边界，第 09 章及最终框架修改必须使用 GPU 完成 profiler、端到端 benchmark 和复现。

两条路径共享接口和事件格式。模拟器用于证明状态和不变量，GPU 实验用于证明真实执行行为；两类证据必须明确标注，不能互相替代。

## 每章必须留下的学习证据

每一章至少提交以下产物：

- 一份运行前预测，保留最初假设。
- 一个能够工作的朴素基线。
- 一个让基线失败的最小反例。
- 一份从原始事件到根因的分析。
- 一份设计决策记录，包含替代方案与成立条件。
- 实现代码以及正确性、不变量和失败路径测试。
- 一份同条件对照结果，明确模拟观察与真实测量的区别。
- 一段迁移说明：新约束出现时，当前结论是否仍然成立。

章节完成不由“运行成功”判定。验收检查学习者能否重新推导方案、解释失败、证明收益并指出风险。

## 代码与课程的分支约定

Git 的 `main` 始终保留已经通过该阶段验收的参考主线。课程开发和学习实验使用短生命周期分支：

- `chapter/<number>-<topic>`：建设一个完整章节及其连续代码状态。
- `lab/<number>-<failure-or-question>`：隔离某个探索、构造或失效 Lab。
- `experiment/<hypothesis>`：保留可复现的性能或策略对照。
- `framework/<name>-<issue>`：进入 vLLM 或 SGLang 的源码修改与验证。

参考答案不会与任务同时出现。每个 Lab 应保留 `baseline`、关键失败状态和通过验收的实现，以便学习者比较设计演进，而不是只看到最终目录。

## 明确不做什么

- 不按 vLLM、SGLang 的功能列表组织章节。
- 不把框架默认配置写成跨版本最佳实践。
- 不用模拟器数据声称真实 GPU 性能收益。
- 不用单一峰值吞吐替代尾延迟、失败率和 goodput。
- 不要求学习者无提示地重新发明整个系统；提示提供现象、工具和约束，但不替代关键设计决策。
- 不在主线中扩张到训练系统、通用分布式训练或与推理主线无关的 CUDA 技巧。

## 初始建设顺序

项目将先完成毕业能力矩阵、统一事件模型和第 00—02 章样板。样板必须完整经历“朴素实现—反例—推导—改造—失效—框架映射”，通过评审后再扩展 KV、调度和压测主线。这样可以先验证教学方法，而不是一次性写完大量仍然像操作手册的内容。
