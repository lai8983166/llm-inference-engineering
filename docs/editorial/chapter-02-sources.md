# 第 02 章来源与编辑记录

## 使用规则

本章只让“多个请求同时存在”进入系统，所有请求仍继承第 01 章的状态、输出和资源合同。正文中的技术陈述按下列三类管理：稳定原理需要能够追溯到规范或一手文档；运行时与框架事实必须记录版本或访问日期；真实效率判断只能由当前软硬件上的原始测量支持。确定性轨迹属于教学模型，不以引用把假设包装成事实。

## 稳定原理

| 待支持主张 | 一手来源 | 可以支持什么 | 不能推出什么 |
| --- | --- | --- | --- |
| 异步提交允许主机在设备工作完成前继续；实际并发取决于硬件能力、资源和 stream 语义 | [NVIDIA CUDA Programming Guide: Asynchronous Execution](https://docs.nvidia.com/cuda/cuda-programming-guide/02-basics/asynchronous-execution.html)，2026-08-23 核对 | 必须分开主机调用返回、设备开始/完成；多个主机控制流活跃不构成 kernel 同时执行的证据 | 不能推出当前 GPU 上一定重叠、一定串行或吞吐一定提高 |
| 同一 stream 中操作按入队顺序执行，多 stream 的调度仍受可用资源和运行时选择影响 | 同上，CUDA Streams 与 Stream Ordering 小节，2026-08-23 核对 | 设备执行顺序需要 stream、event 与设备轨迹，而不能从线程/协程数量猜测 | 不能把课程中的单设备队列当作 CUDA 的普遍调度实现 |
| 变长序列若要组成规则张量，常见做法是把短序列 padding 到 batch 最长长度或指定长度 | [Hugging Face Transformers: Padding and truncation](https://huggingface.co/docs/transformers/main/en/pad_truncation)，`main` 文档，2026-08-23 核对 | 可以解释第 02 章静态 prefill 案例中“有效 token 与对齐位置”的区别 | 不能推出某个推理 kernel 必然计算全部 padding，也不能量化真实浪费 |
| 每个请求的停止、输出提交与资源释放必须独立裁决 | 本项目已验收的 `single-request-pilot` 主规格及第 01 章状态/所有权推导 | 多请求组织不能抹掉请求身份、终止原因、输出许可和 KV 使用权 | 不规定生产框架的具体类名、锁或生命周期 API |

## 必须实测的判断

以下问题在本章只能提出观察需求，不能由教学轨迹给出性能结论：

- 两个请求的 kernel 是否重叠、重叠多少，以及 stream 配置是否引入同步。
- 将请求组成 batch 后的 kernel 时间、显存带宽、算力利用率和端到端吞吐如何变化。
- padding、非活跃槽位或重新组织 batch 在具体模型、形状、框架与硬件上的实际成本。
- 某种执行组织对真实 TTFT、后续 token 间隔、尾延迟、失败率和 goodput 的影响。

真实结论必须沿用第 00 章的测量合同：固定请求集合与生成工作量，记录观察者和完成事件，保留原始事件、失败与环境信息，再限定结论适用范围。

## 确定性教学模型假设

任务组 1 的 `StrategyTrace` 只用于形成可复核的因果轨迹：

- 时间使用离散的 `logicalStep`，不对应毫秒、GPU cycle 或等长真实执行区间。
- 串行策略让一个请求完整结束后再选择下一个，用于隔离队头等待。
- 独立循环策略允许各请求分别提交工作，但抽象设备一次只取一个执行组；这是为了显示“主机并发不等于已经证明设备并行”，不是 CUDA 调度模拟器。
- 静态 batch 等待首批两个请求并固定成员直到该批结束，用于暴露 prompt 对齐、提前结束成员和批外等待；cohort 大小与选择规则不是最佳实践。
- 所有策略使用同一份 `RequestFixture`。任何完成顺序差异只能说明这些明确假设下的事件变化。
